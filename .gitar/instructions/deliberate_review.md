# Deliberate Review Philosophy: Thought Over Velocity

## The Asymmetry of Consequence

In distributed, multi-threaded Minecraft server environments running across thousands of live production instances, the consequences of software defects are severely asymmetrical:

- **Saving a contributor an hour of review friction** produces negligible net value to the project.
- **Letting a subtle defect escape into a release** inflicts hundreds of hours of operational chaos: regional tick deadlocks on Folia, unreleased chunk tickets causing JVM OutOfMemoryError crashes, corrupted chunk headers, or desynchronized admin configurations breaking server networks.

"Developer velocity" that bypasses deliberate design, empirical evidence, and architectural justification is not an asset; it is an engine for generating compounding technical debt and production instability.

Review friction in this repository is an intentional cognitive gate. It compels contributors to pause, trace worst-case failure modes, verify invariant preservation, and provide rigorous proof before changes become irreversible liabilities.

---

## Core Review Principles

### 0. Evidence, Not Percentages
Verdicts are `BLOCKED` or `CLEAR` with counts and clearing conditions (`.gitar/instructions/verdict.md`). Never state a completion percentage.

### 1. Zero Automated Approvals on Functional Code
Automated approvals encourage rubber-stamping and superficial scrutiny. Automated approval must never be granted for pull requests touching bytecode, build logic, or SPI interfaces. Only standalone documentation improvements or formatting fixes in pure markdown may qualify for low-touch verification.

### 2. Probing Assumptions on Critical Execution Paths
When a pull request touches execution pipelines (`rtp-core/.../tasks/teleport/`), resource trackers (`MemoryTracker`), off-tick region decoders (`anvil-api`), or platform schedulers (`rtp-folia/`), Gitar must interrogate the author's assumptions with specific technical inquiries:
- *Worst-Case Execution:* What is the worst-case time and space complexity if regional tick loops are saturated?
- *Exit Guarantees:* If an asynchronous chunk retrieval times out, is canceled, or throws an unhandled exception, what explicit mechanism guarantees the chunk ticket is dereferenced in `MemoryTracker`?
- *Regional Ownership:* If an operation spans across region boundaries mid-flight on Folia, what prevents a `ThreadAccessException`?
- *Failure Propagation:* If a location candidate fails safety or claim validation, how is that failure surfaced to diagnostics and the player without silent drops?

### 3. Penalize Unstructured Complexity (Rule D-008)
When a pull request expands a class with multiple disparate responsibilities (e.g., mixing serialization, geometric validation, and networking into a single class), Gitar raises an advisory citing `Rule D-008` and requests decomposition into package-private cohesive helpers behind a stable public facade. It blocks only if the structure prevents auditing a Critical-blast-radius file with evidence.

### 4. Empirical Evidence as a Prerequisite to Merge
Theoretical assurances of safety are insufficient for high-blast-radius changes. Claims of thread safety, memory leak prevention, or performance parity must be accompanied by empirical evidence generated by repository verification tooling (`scripts/bench_fuzz.py`, devstack acceptance suites, or traceable unit tests).
