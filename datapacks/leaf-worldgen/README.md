# leaf-worldgen

First vanilla-datapack worldgen test case after retiring Iris (see [ADR-005](../../docs/design/adr/ADR-005-retire-iris-for-vanilla-datapack-worldgen.md)).

## What this tests

The "biome within a biome" gradient: a dark forest whose trees scale up the
farther you travel into it, built from three **nested** biomes carved on the
`multi_noise` humidity axis (no edge-distance metric exists in vanilla; the
nesting is produced because humidity is a continuous, low-frequency field, so
its extreme band lands in the interior of large humid regions).

This gradient is now wired into the **real overworld** (not a custom dimension):
`data/minecraft/dimension/overworld.json` overrides the overworld biome source
with the full vanilla multi_noise biome list (generated by the vanilla data
generator `--reports` for this exact server version) with every
`minecraft:dark_forest` **and** `minecraft:taiga` entry split, on its own
humidity span, into thirds -> `leaf:dark_forest_{edge,body,core}` and
`leaf:taiga_{edge,body,core}`. Every other vanilla biome is preserved
verbatim, so only dark forests and taiga change. Because this overrides
`minecraft:` biome placement (not a custom *dimension*), Paper loads it.

The **taiga** family mirrors the dark-forest pattern with conifers, using custom
scaled procedural spruce (full conical crowns, not vanilla "little leaf hats"):
the edge is vanilla taiga, the body steps up to `leaf:spruce_mid` (trunk
base_height 11-16, foliage radius 3-4), the core to `leaf:spruce_large` (trunk
base_height 17-24, foliage radius 4-5), and the core additionally hosts sparse
tree-gen mega-spruce giants (h57-h82, ~W23-26 crowns) placed as a biome-gated
jigsaw structure so their wide crowns overlap into a closed mega-canopy from few
trunks. The mid/large spruce placed wrappers carry the `would_survive` sapling
filter so they ground correctly and do not stack.

| Biome | Trees | Core giants |
|---|---|---|
| `leaf:taiga_edge` | vanilla `minecraft:trees_taiga` | - |
| `leaf:taiga_body` | `leaf:taiga_trees_body` (scaled `leaf:spruce_mid` + vanilla understory) | - |
| `leaf:taiga_core` | `leaf:taiga_trees_core` (scaled `leaf:spruce_large`/`_mid` + understory) | tree-gen mega-spruce `.nbt` (jigsaw, spacing 2/sep 1) |

**Spacing scales with tree size.** Giant jigsaw spacing is tuned to each
species' crown width so wider crowns are spread further apart and narrower crowns
are packed closer, keeping a consistent overlapping canopy. The dark-forest
spiral/titan giants (~45-73 block crowns) use `spacing 4/sep 2` (~2-4 chunks),
while the smaller taiga mega-spruce (~23-26 block crowns) use the tighter
`spacing 2/sep 1`. The same principle applies to the count-based procedural
tiers: the larger-tree core uses a lower per-chunk count than the body
(e.g. taiga core count 8 vs. body count 10) so bigger trees get more spacing.

| Biome | Humidity band | Trees | Foliage tint |
|---|---|---|---|
| `leaf:dark_forest_edge` | `[0.10, 0.35]` | vanilla-like (`minecraft:dark_oak` default, birch/oak, few mushrooms; `count 4`) | light green |
| `leaf:dark_forest_body` | `[0.35, 0.65]` | medium dark oak (`leaf:dark_oak_mid` default, occasional large) | vanilla dark-forest modifier |
| `leaf:dark_forest_core` | `[0.65, 1.00]` | dense `leaf:dark_oak_mid` (`count 18`) + occasional tree-gen giants | deep green |

The split is applied per dark_forest parameter point, so each tier inherits the
same temperature/continentalness/erosion/weirdness window as vanilla dark forest
and only the humidity sub-band differs. Bands are **disjoint** (no overlap) so
adjacent rings meet at a single clean boundary instead of dithering against each
other; as humidity rises toward the wet interior of a dark-forest region you
pass edge (vanilla-like) -> body (medium dark oak) -> core (tall dark oak + giant
tree-gen spiral/titan emergents).

The legacy `leaf:darkforest_test` custom dimension is kept for single-player
vanilla testing only; Paper does not load custom dimensions, but it does load
the overworld override above.

## Plain forest gradient (open canopy)

The same humidity-thirds split is applied to every vanilla `minecraft:forest`
parameter point, producing `leaf:forest_{edge,body,core}`. Unlike the dark
forest, the plain forest is **never roofed**: trees stay sporadic at every tier
so light reaches the floor. Only tree density and size change across the
gradient; the biome is otherwise pure vanilla forest (no `grass_color_modifier`,
no foliage tint).

| Biome | Humidity band | Trees |
|---|---|---|
| `leaf:forest_edge` | driest third | sparse small oak/birch (`leaf:forest_trees_edge`, `count 3`) |
| `leaf:forest_body` | middle third | pure vanilla forest (`minecraft:trees_birch_and_oak_leaf_litter`) |
| `leaf:forest_core` | wettest third | taller `leaf:oak_large`-weighted mix (`leaf:forest_trees_core`, `count 7`) |

The core uses a low per-chunk count (7, vs. the dark-forest core's 18) so its
taller oaks read as an open, light-dappled stand rather than a closed canopy.

## Occasional rainbow flower forest (leaf-only tint gradient)

Every vanilla `minecraft:flower_forest` parameter point is split, on its
humidity span, into **12 equal sub-bands** mapped to `leaf:rainbow_forest_01`
.. `leaf:rainbow_forest_12`. The 12 biomes are byte-for-byte clones of vanilla
flower_forest (same trees, flowers, spawns, sky/water) and differ in **one**
field: `effects.foliage_color`. The 12 colors are an even 12-step hue gradient
(HSV `s 0.55`, `v 0.80`, 30 degrees apart) so adjacent strips ease into one
another instead of clashing.

Because humidity is a continuous low-frequency field, the 12 disjoint bands
land as adjacent strips across each flower forest, so the **leaf canopy** reads
as a rainbow that drifts hue as you walk. Only `foliage_color` is set (no
`grass_color`), so the tint lands on leaf blocks (and vines) while grass keeps
its default flower-forest green -- per the "tint only the leaves" design. Flower
forests are already a rare biome, so the rainbow stays occasional.

| Aspect | Value |
|---|---|
| Biomes | `leaf:rainbow_forest_{01..12}` |
| Tinted | leaf blocks + vines only (`foliage_color`); grass unchanged |
| Gradient | 12 hues, 30 degrees apart, `HSV(s 0.55, v 0.80)` |
| Placement | each `minecraft:flower_forest` humidity span split into 12 disjoint sub-bands |

Regenerate the biome JSONs with
`python tools/build_rainbow_biomes.py` (adjust `N`/`SAT`/`VAL` there to retune
the palette), then rebuild the overworld override (the `minecraft:flower_forest`
entry in the `SPLITS` map of `tools/build_overworld_override.py` derives its 12
tiers from the same count).

> **Regenerating the override:** the overworld biome list is version-specific.
> To rebuild it for a new MC version, run the vanilla data generator with the
> matching JDK (the server jar needs JDK 25 for 26.1.x):
> `java "-DbundlerMainClass=net.minecraft.data.Main" -jar <mojang-bundler>.jar --reports`
> then re-split each `minecraft:dark_forest` and `minecraft:taiga` entry's

> **Paper caveat (dimensions only):** Paper/Spigot do **not** load custom
> datapack *dimensions*, so `leaf:darkforest_test` returns *unknown dimension*
> on the server. Custom *biomes* and an overridden `minecraft:overworld` biome
> source DO load, which is why the gradient now ships in the overworld.

(it overrides vanilla tree features) and works on Paper.

## Forest tree-scale test (general overworld)

Separate from the dark-forest gradient (now wired into the overworld biome
source above), this pack also exercises the **tree scale model** in ordinary
`minecraft:forest`/`minecraft:plains` by overriding two vanilla tree configured
features with size-graded oak selectors. This is an in-biome size *mix* (no
concentric rings); it complements the dark-forest tier gradient:

`minecraft:trees_birch_and_oak_leaf_litter` (the feature `minecraft:forest`
actually uses on this server version - the older `minecraft:trees_birch_and_oak`
no longer exists, so overriding only that name had no effect on forests):

| Variant | Trunk | Canopy | Selector weight |
|---|---|---|---|
| `leaf:oak_large` | fancy branching giant, `base_height 15` (+0..11) -> 15-26 block trunk, 20+ overall | `fancy_foliage_placer radius 3, height 4, offset 4` | `chance 0.08` |
| `leaf:oak_medium` | `base_height 5` (+0..2) | blob `radius 2, height 2` | `chance 0.25` |
| `leaf:oak_small` | `base_height 2` (+0..1) | blob `radius 1, height 1` | `chance 0.20` |
| `leaf:birch_tall` | `base_height 5` (+0..2, +6 extra) | blob `radius 2, height 3` | `chance 0.10` |
| `leaf:birch_short` | `base_height 4` (+0..1) | blob `radius 2, height 2` | `chance 0.10` |
| `leaf:birch` | vanilla | vanilla | `chance 0.05` |
| `minecraft:oak` (default) | vanilla | vanilla | remainder |

Multiple size variants **per species** (three oak sizes + three birch sizes)
are layered into the selector so each forest reads as a varied natural mix
rather than a binary tall/short split.

`minecraft:trees_plains` (used by `minecraft:plains` - usually right at spawn,
so the scale model is visible immediately without hunting for a forest):

| Variant | Selector weight |
|---|---|
| `leaf:oak_large` | `chance 0.12` |
| `leaf:oak_medium` | `chance 0.25` |
| `leaf:oak_small` | `chance 0.15` |
| `leaf:birch_tall` | `chance 0.10` |
| `minecraft:oak` (default) | remainder |

`leaf:oak_large` is modelled on vanilla's *fancy* (large) oak - it uses
`fancy_trunk_placer` (branching trunk) + `fancy_foliage_placer`, so it reads as
a natural, branching giant rather than a straight pole topped by a single
bloated leaf-ball (the earlier `straight_trunk_placer` + `blob_foliage_placer`
looked non-vanilla and never branched).

The `leaf:oak_{large,medium,small}` and `leaf:birch{,_short,_tall}`
**placed-feature** wrappers each carry a `block_predicate_filter`
(`would_survive` oak/birch sapling), matching
the vanilla tree placed features used inside these selectors. This is required:
`minecraft:forest` places trees with `count` (~10/chunk) + an `OCEAN_FLOOR`
heightmap that counts logs, so without the survive filter each pick re-snaps
onto the previous tree's trunk and stacks trees vertically to the build limit.
(Plains avoided this only because its outer `trees_plains` placed feature
already has the filter.)

So a normal overworld forest shows a dramatic mix of towering and dwarf oaks,
and even spawn-area plains drop occasional towering lone oaks. This is an
**in-biome size mix** (no edge-distance metric exists for ordinary biomes); the
**concentric** edge->core gradient is provided separately for dark forests by
the overworld biome-source override described at the top of this file.

## Core trees: density feature + landmark giants

The core ring layers the two ways vanilla can place trees (which Iris collapsed
into one object-placement path):

- **Per-chunk density (Option B):** `leaf:dark_oak_mid` is a `minecraft:tree`
  feature (taller `dark_oak_trunk_placer`, `base_height 9`) used as the
  `random_selector` default in `dark_forest_trees_core`, so the whole core
  canopy is visibly taller/denser than vanilla dark oak.
- **Rare landmark giants (Option A):** the tree-gen `titan`/`spiral` giants
  (exported to vanilla structure `.nbt`) are placed as a biome-gated jigsaw
  structure (`leaf:dark_forest_giant`), gated to `leaf:dark_forest_core` via
  the `#leaf:has_structure/dark_forest_giant` biome tag and spaced by
  `dark_forest_giants` (random_spread). These are the *exact* tree-gen
  geometry and appear as occasional signature giants in the forest heart.

Regenerate the giant `.nbt` from `tools/tree-gen`:

```
python tools/tree-gen/generate_tree.py \
  --config tools/tree-gen/configs/dark-forest-giants.json \
  --format nbt --data-version 4325 \
  --out datapacks/leaf-worldgen/data/leaf/structure/dark_forest
```

### Maple Forest birch speciation (landmark birch)

Maple Forest is a **warm multicolor variant set** (`leaf:maple_forest_01..08`),
the warm-palette cousin of the `leaf:rainbow_forest_NN` rainbow forest: 8 biomes
that differ only in `effects.foliage_color`, stepping across the warm arc (deep
red -> orange -> amber -> gold) so the canopy reads as an autumn-harvest
gradient. They are generated by `tools/build_maple_biomes.py` and banded across
`minecraft:birch_forest`'s humidity span by `_maple_tiers()` in
`tools/build_overworld_override.py` (same trick as the rainbow split). Like the
rainbow set, each variant uses the oak-only `leaf:rainbow_trees` placed feature
so the foliage tint reads cleanly (birch leaves use a fixed hardcoded colour).

The set also gets its own birch **speciation** landmark: tall, branching birch
templates generated by `tools/tree-gen` (`birch` profile, `birch_log` /
`birch_leaves`). They are placed exactly like the dark-forest/taiga giants - a
biome-gated jigsaw structure (`leaf:maple_forest_giant`), gated to all of
`leaf:maple_forest_01..08` via the `#leaf:has_structure/maple_forest_giant`
biome tag and spaced by `maple_forest_giants` (random_spread, `salt 80093`).

Regenerate the birch `.nbt` from `tools/tree-gen`:

```
python tools/tree-gen/generate_tree.py \
  --config tools/tree-gen/configs/maple-birch-giants.json \
  --format nbt --data-version 4325 \
  --out datapacks/leaf-worldgen/data/leaf/structure/maple_forest
```

## How to test (server boot is user-triggered)

Deploy with `datapacks/deploy-datapacks.ps1` (copies each `datapacks/<pack>`
into `<ServerBase>\<LevelName>\datapacks\<pack>`; use `-Only leaf-worldgen` to
deploy just this pack), or copy/symlink this folder into the world's
`datapacks/` directory manually. To clear stale chunk data and regenerate FROM
SCRATCH, add `-ResetWorld` (moves the old world to a timestamped backup unless
`-NoBackup` is given). Worldgen changes only appear in **newly generated
chunks** -- a `/reload` is **not** enough.

### A. Overworld tree-scale test (works on Paper)

1. Deploy (optionally with `-ResetWorld`) and boot the server.
2. Spawn is usually `minecraft:plains`: with `-ResetWorld` the spawn area is
   freshly generated, so you should already see occasional **towering lone
   oaks** (and dwarf oaks) among the grass.
3. For the full effect, reach a freshly-generated `minecraft:forest` /
   `minecraft:flower_forest` (`/locate biome minecraft:forest`): it should show
   a dramatic mix of towering (`leaf:oak_large`) and dwarf (`leaf:oak_small`)
   oaks. Already-generated chunks keep their old trees, so you must reach
   **new** chunks (a `/reload` is not enough).

### B. Dark-forest gradient dimension test (vanilla single-player only)

> Skipped on Paper: the custom dimension is not loaded there (see the Paper
> caveat above). Run this in single-player vanilla or a vanilla dedicated
> server.

1. Load the world with the pack active and run `/reload` if needed.
2. Teleport into the test dimension:
   `/execute in leaf:darkforest_test run tp @s 0 320 0`
   then drop to the surface, or use spectator + large render distance.
3. Walk from a forest edge toward its interior: tree density and size should
   increase (sparse small -> standard -> dense taller `dark_oak_mid`) and the
   foliage tint should deepen, with no patchy alternation between rings. The
   core should also contain occasional towering tree-gen giants.

### Spot-checking a giant with `/place`

`/place structure leaf:dark_forest_giant` (run while standing in
`leaf:dark_forest_core` on vanilla) is a quick visual check, but **it is not
representative of worldgen placement**: `/place` drops the template at your
exact feet position and ignores the structure's
`project_start_to_heightmap: WORLD_SURFACE_WG`, so the tree appears to float
~6-10 blocks (the template's empty padding below the trunk base). During real
worldgen the start jigsaw block IS projected to the surface heightmap, so the
trunk lands on the ground.

## Target version

Authored against the 1.21.5 biome schema (`pack_format 71`,
`supported_formats [61, 71]`).

## Known follow-ups (not in this test)

- The giants are placed with `terrain_adaptation: none` (trees sit on the
  surface heightmap); revisit if trunk bases need foundation carving on steep
  terrain.
- "Scale up all biomes globally" (larger biome regions) is a `noise_settings`
  / `noise_router` frequency edit (architecturally significant) - to be
  captured separately, not part of this dimension test.
