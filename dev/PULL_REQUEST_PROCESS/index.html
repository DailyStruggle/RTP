    Pull Request Process¶

    Operational guide and reference for preparing, opening, testing, reviewing, and merging Pull Requests (PRs) in the RTP repository.

    This document serves as the canonical Single Source of Truth (SSoT) for the Pull Request lifecycle, connecting implementation and verification to the repository's main line.

    1. Lifecycle Overview¶

    Every code and documentation change intended for the core repository follows a structured lifecycle:

    flowchart TD
    A[Branch from V3] --> B[Implementation & Local Verification]
    B --> C[Local Pre-PR Gates]
    C --> D[Open Pull Request on GitHub]
    D --> E[Automated CI Verification]
    E -->|Failure| B
    E -->|Success| F[Review & Triage]
    F -->|Changes Requested| B
    F -->|Approved| G[Definition of Ready to Merge]
    G --> H[Merge into V3]
    H --> I[Post-Merge Automation]

    2. Branching Strategy¶

    1. Base Branch:
    2. Active development targets the V3 branch (the default branch).
    3. Maintenance backports for older releases target V2 or V1 only when explicitly requested.
    4. Branch Naming: Branches must follow descriptive prefix patterns:
    Change Type Branch Pattern Example
    Bug fix fix/<short-description> fix/chunk-leak-on-reload
    New feature feature/<short-description> feature/rectangle-shape
    Documentation docs/<short-description> docs/pr-process-guide
    Performance perf/<short-description> perf/spiral-lookup-caching
    Refactoring refactor/<short-description> refactor/command-parameter-cleanup
    Release prep release/<version> release/3.3.0
    1. Branch Hygiene:
    2. Keep branch history clean and focused on a single logical change.
    3. Rebase or merge against updated upstream/V3 to resolve conflicts prior to review.

    3. Preparation & Architecture Gates¶

    Before or during development, verify that your changes adhere to repository governance:

    1. Propose Before Implementation (Rule D-005):
    2. If a change touches more than one class, crosses a module boundary, or introduces a new command architecture, a written proposal must be submitted and approved before writing code.
    3. Detail affected modules, before/after structure, relevant REQ-* requirements or ADRs, and trade-offs.
    4. Safety Prohibitions (S-001..S-007):
    5. S-001: Zero unsafe teleport destinations.
    6. S-002: Zero leaked force-loaded chunks (tickets must release on all paths via MemoryTracker).
    7. S-003: Respect land protection plugins.
    8. S-004: Zero silently discarded teleport failures; report and log all errors.
    9. S-005: Zero main-thread chunk I/O or blocking .get() calls.
    10. S-006: Throw IllegalStateException on early API access before core initialization.
    11. S-007: Configurable failure and command error messages via messages.yml.
    12. Regional Threading & Concurrency:
    13. On Folia, verify region thread ownership via Bukkit.isOwnedByCurrentRegion before regional dispatch (Rule F-001).
    14. All asynchronous or scheduled tasks must use RTP.scheduler (RTPScheduler SPI); never spawn raw threads.
    15. Requirements Traceability (4-Step Workflow): When introducing or modifying a functional or architectural requirement:
    16. Add the requirement to docs/dev/REQUIREMENTS.md (or submodule REQUIREMENTS.md) with the next sequential ID (REQ-<module>-<family>-NNN).
    17. Add a row to docs/dev/TRACEABILITY.md binding the requirement to its design reference, implementing class, and test.
    18. Update docs/dev/DESIGN.md if the change introduces an architectural mechanism.
    19. Add or update an automated unit or ArchUnit test.

    4. Local Pre-PR Verification Gates¶

    Contributors must run local verification gates before pushing a branch or opening a pull request. This ensures fast feedback and avoids avoidable CI failures.

    Quick Verification Checklist¶

    # 1. Code formatting
./gradlew spotlessApply

# 2. Traceability validation
./scripts/check_traceability.sh

# 3. Encoding and mojibake check
python scripts/check-mojibake.py

# 4. Front page copy validation
python scripts/release/build_front_pages.py --check

# 5. Public API binary compatibility check
./gradlew checkBinaryCompatibility

# 6. Targeted or full test run
./gradlew test

# 7. Coverage and static analysis gates (ADR-094)
./gradlew check -Pcoverage -PstaticAnalysis

# 8. Changed-line coverage gate (minimum 80% coverage on changed lines)
python scripts/diff-coverage.py --baseline origin/V3 --min 0.80

    Gate Details¶

    • Code Formatting (Spotless): Enforces consistent formatting across Java source files. Running ./gradlew spotlessApply automatically resolves discrepancies.
    • Traceability Gate (check_traceability.sh): Parses all REQUIREMENTS.md files and verifies that every REQ-* identifier has an associated row in docs/dev/TRACEABILITY.md. CI fails if any requirement is untraced.
    • Mojibake & UTF-8 Scanner (check-mojibake.py): Ensures all markdown, configuration, and source files are plain UTF-8 without byte-order marks (BOM) or corrupted encoding characters.
    • Storefront Page Check (build_front_pages.py --check): Verifies that storefront templates and copy generated from docs/publishing/FRONT_PAGE.md remain consistent and uncorrupted.
    • Binary Compatibility (japicmp): Compares public API signatures (rtp-api, commands-api, effects-api, maps-api, metrics-api, anvil-api, tags-api) against the baseline release. Any non-deprecated breaking change fails unless recorded in the accepted breaks registry (ADR-094, DEPRECATION_POLICY.md).
    • Testing Tier Selection:
    • Localized module changes: Run targeted tests (e.g. ./gradlew :rtp-core:test --tests "*Selection*").
    • Cross-module interface or root Gradle changes: Run a full multi-module build (./gradlew build).
    • Documentation-only changes: Exempt from build and test runs.
    • Static Analysis (PMD): Under -PstaticAnalysis, evaluates rules in config/pmd/ruleset.xml, including the custom PreferNonLockingExecution check.
    • Changed-Line Coverage Gate (diff-coverage.py): Evaluates JaCoCo per-line coverage for lines added or modified against the base branch (origin/V3). Fails if covered fraction falls below 80% (0.80).
    • Multi-Server & Acceptance Harness (Devstack): If touching cross-server network mode, proxy protocols, reservation tokens, or multi-platform container parity, execute headless acceptance: 
      .\devstack\run-acceptance.ps1 -Scenario all
      (or ./devstack/run-acceptance.sh --scenario all on Linux).

    5. Documentation & Metadata Synchronization¶

    Every PR must keep documentation in lockstep with code:

    1. CHANGELOG.md:
    2. Add a bullet under ## [Unreleased].
    3. Describe the net delta against the last released tag in absolute phrasing.
    4. Do not include Pro-exclusive markers or retired edition tags (ADR-100, ADR-108).
    5. docs/dev/TRACEABILITY.md:
    6. Update rows for any new or modified requirements.
    7. docs/MIGRATION.md:
    8. Required if a breaking public API change or major configuration structure change is introduced.
    9. Locale Parity (lang/):
    10. When adding user-facing keys to rtp-plugin/src/main/resources/messages.yml or config.yml, mirror the keys across lang/<file>.lang.yml and all lang/<locale>/<file>.yml.
    11. Validate with ./gradlew :rtp-plugin:test --tests "*LocaleParityTest*".
    12. Architectural Records (ADR):
    13. New significant architectural decisions require an ADR under docs/adr/ (or <subproject>/docs/adr/) and a catalog entry in docs/adr/README.md.

    6. Authoring the Pull Request¶

    PR Title¶

    Use clear, imperative titles prefixed by category: - fix: release chunk tickets on player disconnect during teleport - feat: implement polygon shape with concave boundary support - docs: add comprehensive pull request workflow guide - perf: optimize spiral coordinate lookup cache

    PR Description & Template¶

    GitHub automatically populates .github/PULL_REQUEST_TEMPLATE.md. Complete all sections:

    1. Description:
    2. Plain-language summary of what was changed and why.
    3. Reference any relevant issues (e.g. Fixes #123 or Linear tracker issue RTP-45).
    4. Related Requirements:
    5. List associated REQ-* IDs (e.g. REQ-CORE-F-001, REQ-RTP-S-002).
    6. Type of Change:
    7. Mark the relevant category (Bug fix, New feature, Refactoring, Documentation, Build/CI).
    8. Checklist:
    9. Verify every item honestly (tests passing, traceability checked, changelog updated, binary compatibility).
    10. Test Evidence:
    11. Provide command outputs, test run summaries, benchmark results, or screenshots demonstrating verification.

    7. Continuous Integration (CI) Pipeline Anatomy¶

    Pull requests trigger automated GitHub Actions workflows configured in .github/workflows/gradle.yml:

    flowchart LR
    subgraph CI["GitHub Actions (gradle.yml)"]
        direction TB
        A["build-reduced-jdk21\n(JDK 21 Sandbox & Exclusion Assemble)"]
        B["build-full\n(JDK 21 + 25, Toolchains, All Carriers)"]
        B --> C["Spotless & Binary Compatibility"]
        B --> D["Full Build & ShadowJar"]
        B --> E["Static Analysis (PMD) & JaCoCo Coverage"]
        B --> F["Changed-Line Coverage Gate (>= 80%)"]
        B --> G["SonarCloud Analysis (when token present)"]
    end

    Job Descriptions¶

    1. build-reduced-jdk21:
    2. Runs on Ubuntu with Temurin JDK 21.
    3. Validates the reduced build variant using exclusion flags: -PexcludeJdk25 -PexcludeNeoforge
    4. Executes ./gradlew assemble to guard against silent degradation of offline sandbox and JitPack environments without duplicating full test suites.
    5. build-full:
    6. Provisions both JDK 21 and JDK 25 toolchains with gradle/actions/setup-gradle.
    7. Compiles the full unified JAR, including modern Fabric and NeoForge deobfuscation carriers.
    8. Executes Spotless verification, japicmp public API compatibility checks, and full multi-module tests.
    9. Enables coverage and static analysis via -Pcoverage -PstaticAnalysis.
    10. Executes SonarCloud analysis (when SONAR_TOKEN is present), reusing build bytecode, PMD reports, and JaCoCo XML.
    11. Executes scripts/diff-coverage.py against the base ref (origin/V3), enforcing the 80% coverage threshold on modified code.
    12. Publishes test reports and uploads coverage and binary artifacts.

    Auxiliary Workflows¶

    • Documentation Site (docs.yml): Validates MkDocs Material configuration and deploys to gh-pages upon merge to V3.
    • Nightly Acceptance (devstack-acceptance.yml): Runs multi-server proxy and backend cluster integration scenarios using headless Mineflayer bot drivers.
    • Weekly Mutation Testing (mutation-testing.yml): Executes PIT mutation tests across critical safety packages (threshold >= 60%).

    8. Review, Revision & Merge¶

    Review Expectations¶

    1. Safety First: Reviewers verify compliance with prohibitions S-001 through S-007. Code violating these invariants will not be approved.
    2. Threading Soundness: No blocking thread operations or foreign-region accesses on Folia regional schedulers.
    3. Addressing Review Comments:
    4. Push follow-up commits to the existing PR branch.
    5. Avoid force-pushing over existing review history unless cleaning up commits prior to final squash.
    6. Reply directly to review comments indicating the resolution or rationale.

    Definition of Ready to Merge¶

    A pull request is ready to merge when all of the following conditions are satisfied:

    • [ ] All automated CI status checks are passing (green).
    • [ ] At least one maintainer review approval is granted.
    • [ ] Any architectural change conforms to an approved Rule D-005 proposal and ADR.
    • [ ] CHANGELOG.md reflects the change under [Unreleased].
    • [ ] Any added or modified requirements are traced in docs/dev/TRACEABILITY.md.
    • [ ] If breaking public API changes were introduced, docs/MIGRATION.md is updated.
    • [ ] Changed-line test coverage meets or exceeds 80%.
    • [ ] Encoding hygiene is maintained (UTF-8, no BOM, zero mojibake).

    Merging & Post-Merge¶

    • PRs are merged into V3 (typically via Squash and Merge to maintain a linear, bisectable commit history).
    • The squash commit message should follow repository conventions and reference the PR number.
    • Post-merge automation compiles and archives release artifacts and triggers documentation site publication.
