    PROPOSAL: GUI-author SPI (menu data + teleport intent) for third-party inventory GUIs¶

    Status: Proposal (this file). Author: Junie, 2026-05-29 (revised 2026-05-30). Captures the design conversation between the user and Junie so the implementation can resume in a later session without re-deriving any decision. No code lands in the session that produced this file. Rule D-005: this proposal must be approved before any code is written.

    Revision 2026-05-30 - prior-art reconciliation: The teleport-intent entry point this proposal originally called requestTeleport(...) already exists in rtp-api as RTPAPI.teleport(UUID, RtpTarget) -> CompletableFuture<RTPResult> (plus cancel, queueDepth, isWarmingUp), shipped and tested as Phase 1 of CHECKLIST-rtp-api-devux.md (RtpApiTeleportSurfaceTest, TeleportDataTest). RtpTarget and RTPResult value types also already exist in rtp-api. This proposal is therefore narrowed: the mutating intent call is done; what remains is the read/metrics/chart surface plus the unstable rtp-core hooks. Do not re-author a requestTeleport(...) - reuse RTPAPI.teleport(...). (Note: the core-internal Region/RegionQueueManager.requestTeleport(UUID) is unrelated waitlist enrollment, ADR-043, not a public API.)

    1. One-paragraph summary¶

    RTP ships a book-first interactive menu framework (ADR-035), maps-api for chart/MSPT rendering onto map items, and metrics-api for runtime-health snapshots. A native inventory (chest) GUI was evaluated and found to carry a poor cost/risk ratio: books already cover destination pickers and dense config text, maps-api already covers time-series visualizations (e.g. MSPT), and a chest renderer would require a parallel Fabric screen-handler implementation plus ownership of inventory-specific vulnerability surface (click races, item-dupe vectors, click-spam). Rather than ship and own an inventory GUI, this proposal exposes a small, safe GUI-author SPI so third-party GUI plugins/addons can build inventory (or any) GUIs against RTP. RTP owns validation and safety; the GUI author owns presentation and click handling. The surface is split between rtp-api (public, semver-stable, advertised to authors) and rtp-core (callable-but-unstable hooks for deeper introspection).

    2. Decisions captured from the conversation¶

    These are the answers the user gave during the design discussion. They are the contract this design is built against; do not silently change them in implementation.

    1. Do not ship a native inventory GUI. The remaining exclusive advantages (in-place toggle grids, slot/drag/quantity semantics, dashboard tile density) do not outweigh the cross-platform maintenance + security cost of RTP owning a chest renderer.
    2. MSPT (and any time series) is maps-api's job, fed by metrics-api (MetricsSnapshot.mspt, tickBudgetUtilisation = mspt/50; on Folia FoliaRegionSample.mspt is per-region). The SPI exposes this as a ChartSpec-style request, not raw item-drawing primitives.
    3. Security boundary is the whole point. The SPI exposes intent-level operations only (submit a validated teleport intent via the existing RTPAPI.teleport(...), read permission-gated data). It never exposes raw teleport primitives, item-stack mutation, inventory slot wiring, or click handlers. S-001..S-007 enforcement and permission gating stay inside RTP regardless of what the GUI does. A GUI author cannot, through this SPI, cause an unsafe teleport, bypass claims, or load chunks on the main thread.
    4. Two-tier surface. rtp-api carries the stable, advertised contract; rtp-core is a valid interface for non-topical / deeper hooks that RTP does not want to freeze into the public API. Both preserve the same safety boundary; only the stability guarantee differs.
    5. Books stay the default renderer for player-facing pickers and config text; chat renderer remains the universal fallback. The SPI is additive, not a replacement for the existing menu/ framework.

    3. API surface¶

    3.1 rtp-api (public, semver-stable, no platform imports)¶

    Advertised to GUI authors. Everything returns immutable DTOs or accepts validated intents.

    • Teleport intent (the only mutating call) - ALREADY SHIPPED. 

      // io.github.dailystruggle.rtp.api.RTPAPI - present today.
// Permission, cooldown, cost, and S-001..S-007 safety are enforced inside this call.
// The future always completes with a success/failure RTPResult (S-004); never a silent no-op.
CompletableFuture<RTPResult> teleport(UUID player, RtpTarget target);
boolean cancel(UUID player);          // cancel a pending/in-flight teleport
int     queueDepth(RTPWorld<?> world);// pre-verified ready locations for a world
boolean isWarmingUp(UUID player);     // teleport requested but not yet completed
      No new teleport primitive is needed - this surface already exists and is tested (RtpApiTeleportSurfaceTest, TeleportDataTest). GUI authors call RTPAPI.teleport(...) directly. The RtpTarget selector (defaultRegion(), region(name), world(name), world(RTPWorld)) and RTPResult outcome type are likewise already public in rtp-api.

    • Permission-gated reads (for populating menu items). 

      // Targets this player is actually allowed to use (permission gates already applied).
// Keyed by UUID for consistency with the shipped teleport(UUID, RtpTarget) surface.
List<RtpTarget> getAllowedTargets(UUID player);
// Per-player status for a target: remaining cooldown, cost, availability reason.
RtpTargetStatus getTargetStatus(UUID player, RtpTarget target);
      RtpTargetStatus is a new immutable DTO (remaining-cooldown ms, cost, enum availability reason such as READY / ON_COOLDOWN / NO_PERMISSION / NO_FUNDS / DISABLED). Reuse MenuPermissionGates logic behind getAllowedTargets so the picker matches what the command would allow.

    • Runtime-health read (for dashboard tiles). 

      MetricsSnapshot getMetricsSnapshot();              // global
// (Folia) optional per-region samples for region-scoped tiles.
List<FoliaRegionSample> getRegionSamples();
      Returns sampled snapshots only - never computes on the caller's thread, so no chunk I/O and no main-thread cost is introduced (consistent with maps-api ReqRtpMap002NoChunkIoTest).

    • Chart request (delegates rendering to maps-api). Publish/confirm maps/ChartSpec as the supported way to ask for a rendered chart (MSPT sparkline, etc.) so authors do not draw pixels themselves. Authors hand a ChartSpec + a MetricsSnapshot-derived series to the maps pipeline; RTP/maps-api owns the MapBinding and render constraints.

    • Bring-your-own-renderer hook (already present). The existing menu/ SPI (MenuRenderer, MenuModel, MenuPage, MenuFragment, MenuLine, MenuAction, MenuOpenRequest, MenuConsumerProfile, MenuPlatformView) already lets an author register a renderer. An inventory GUI is simply another MenuRenderer the author supplies - RTP does not write it. Document this path explicitly in the author guide.

    3.2 rtp-core (callable-but-unstable hooks)¶

    For authors who want deeper access and accept breakage between minor versions. Documented as "callable but unstable; not covered by the rtp-api semver guarantee."

    • Live queue/cache introspection (read-only): kept/unkept/backlog/login buffer depths, per-player fast-cache presence - useful for "X locations ready" dashboard tiles. Read-only views, never mutators.
    • The concrete menu builders (FrontPageBuilder, AdminPanelBuilder, CommandTreeMenuBuilder, VisualizationsSubmenuBuilder) for authors who want to mirror RTP's own pages rather than author from scratch.
    • Region/pool metadata (names, distance ranges, biome filters) beyond what RtpTarget exposes.

    Even at this tier, no mutator that could bypass safety/permission is exposed; introspection is read-only and teleport still routes through the existing RTPAPI.teleport(...).

    4. Affected modules¶

    • rtp-api - teleport intent (teleport/cancel/queueDepth/isWarmingUp), RtpTarget, and RTPResult already exist - no work. New work: getAllowedTargets/getTargetStatus reads (on RTPAPI or a new RtpMenuDataApi facade), new RtpTargetStatus DTO, metrics accessors, confirm maps/ChartSpec as public, document the menu/ BYO-renderer path. No platform imports.
    • rtp-core - implement the rtp-api methods (wire getAllowedTargets to MenuPermissionGates, getMetricsSnapshot to CoreMetrics), expose the read-only introspection hooks.
    • No platform-adapter changes required for the SPI itself; adapters already install MetricsBinding / MapBinding. A third-party GUI links rtp-api (and optionally rtp-core).
    • Docs - author guide (where to depend, the safety contract: "RTP owns validation; you own presentation + click handling"), and an ADR.

    5. Requirements / ADR linkage¶

    • Safety prohibitions preserved by construction: S-001 (no unsafe destination), S-003 (no claim-protected teleport), S-004 (no silently discarded failure - RTPAPI.teleport(...) completes its future with an RTPResult), S-005 (no main-thread chunk I/O - reads are sampled snapshots), S-006 (require-by-contract: rtp-api entry points throw IllegalStateException if called before core loads, never null/no-op; already enforced by the shipped teleport surface).
    • Builds on ADR-035 (interactive menus, book-first), ADR-044 (command-tree menu reflector), maps-api (ChartSpec, renderers), metrics-api (MetricsSnapshot).
    • New ADR required: "GUI-author SPI: menu-data + teleport-intent surface, split rtp-api (stable) / rtp-core (unstable hook)." Records the decision NOT to ship a native inventory GUI and the security rationale for the intent-only boundary.

    6. Risks and trade-offs¶

    • API-surface permanence. Anything in rtp-api is a semver commitment. Mitigation: keep the stable surface minimal (intent + permission-gated reads + ChartSpec); push everything speculative into the rtp-core unstable tier.
    • Author misuse outside the boundary. A GUI author can still write an unsafe inventory (dupe bug in their click handler) - but they cannot make RTP perform an unsafe teleport. That is the explicit point: RTP's liability stops at the validated intent. Must be stated plainly in the author guide.
    • Discoverability. An SPI nobody adopts adds maintenance for no usage. Mitigation: ship a tiny example addon under addons/ demonstrating an inventory picker built on the SPI (proves the surface is sufficient and doubles as documentation).
    • RtpTargetStatus shape churn. The availability-reason enum may grow. Keep it an enum with a documented "unknown reasons may be added" note.

    7. Out of scope¶

    • RTP shipping its own inventory/chest renderer.
    • A Fabric MapBinding (separate effort; until it exists, map-item tiles fall back to scalar items on Fabric).
    • Cross-server / network-mode menu data.
    • Any change to the existing book/chat renderers' behavior.

    Phase 1 landed (approved 2026-05-30; user chose: extend RTPAPI directly, defer the example addon, phase the work):

    • New rtp-api DTO RtpTargetStatus (Availability enum: READY / ON_COOLDOWN / NO_PERMISSION / NO_FUNDS / DISABLED / UNKNOWN; remaining-cooldown ms; cost). Immutable, forward-compatible enum.
    • New RTPAPI reads: getAllowedTargets(UUID), getTargetStatus(UUID, RtpTarget), getMetricsSnapshot(), getRegionSamples() - all with REQ-RTP-S-006 pre-init IllegalStateException guards and null-arg validation; null delegate results degrade to a safe non-null value (empty list / UNKNOWN status), never a silent no-op.
    • Core wiring in RTP.java static block: permission-gated target list (region requirePermission + rtp.regions.<name> / rtp.worlds.<name>), per-target status (cooldown from latestTeleportData + player.cooldown(), cost from region price + EconomyKeys.price honouring rtp.free, funds vs balanceFloor), and metrics-api snapshot supplier from RTP.metrics.
    • Build edge: rtp-api now api project(':metrics-api') (acyclic; metrics-api is dependency-free).
    • Tests: RtpApiMenuDataSurfaceTest (13 cases, rtp-api/metrics-api imports only). Full multi-module build green.
    • Follow-up (not blocking): add RtpApiMenuDataSurfaceTest to the REQ-RTP-S-006 row in TRACEABILITY.md (the oversized row resisted in-place editing this session).

    Phase 2 landed ("undefer", 2026-05-30):

    • maps/ChartSpec confirmed already public in rtp-api (io.github.dailystruggle.rtp.api.maps.ChartSpec, renderer-neutral record, REQ-RTP-MAP-006 / ADR-047) and tested (ChartSpecSurfaceTest). No new work was required to advertise it; item 3 is satisfied as-is.
    • New unstable rtp-core introspection hook: io.github.dailystruggle.rtp.common.api.RtpCoreIntrospection (static, read-only) + immutable RegionQueueDepths record. Reports per-region kept/unkept/backlog/login/networkKept/networkReserved buffer depths, waitlist size, open per-player-queue count, and hasFastLocation(region, uuid) presence.
    • Safety: strictly read-only, no mutator exposed; reads are instantaneous in-memory samples (no chunk I/O, S-005). Deliberately degrades to empty/null/false rather than throwing pre-init (the REQ-RTP-S-006 throw contract governs the rtp-api surface, not this unstable hook).
    • Widened RegionQueueManager.hasFastLocation(UUID) from package-private to public so the facade (different package) can read it.
    • Tests: RtpCoreIntrospectionTest (5 cases).

    Phase 3 landed ("create the addon", 2026-05-30):

    • New reference addon addons/RTP_GuiAddon (Bukkit JavaPlugin, /rtpgui) - a chest-inventory destination picker built only on the stable rtp-api surface (compileOnly project(':rtp-api') + :metrics-api; deliberately does NOT link rtp-core, proving the public surface is sufficient for a full GUI).
    • Demonstrates the security boundary: one slot per getAllowedTargets(UUID) target, each decorated via getTargetStatus(UUID, RtpTarget) (availability / cooldown / cost icon + lore), a server-health tile from getMetricsSnapshot(), and click -> RTPAPI.teleport(UUID, RtpTarget). The addon owns presentation + click handling (custom InventoryHolder, cancel-every-click anti-dupe guard); RTP re-validates every teleport.
    • Files: RTPGuiAddon, DestinationPickerGui, DestinationPickerListener, plugin.yml, README.md. Registered as addons:RTP_GuiAddon in settings.gradle. Bukkit-family only (Fabric has no Bukkit inventory API; noted in README).

    9. Open questions for the user¶

    All resolved. The user chose: extend RTPAPI directly, phase the work, then "undefer" the Phase 2 items (ChartSpec confirmation + rtp-core hooks), and finally "create the addon" (Phase 3, the RTP_GuiAddon example). All proposal items are now landed.
