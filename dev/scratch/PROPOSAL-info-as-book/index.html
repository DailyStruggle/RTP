    PROPOSAL: /rtp info as a book GUI (with periodic refresh + text fallback)¶

    Status: Draft (D-005 design, pre-implementation) Date: 2026-05-18 Author: Junie (agent) Predecessors: - PROPOSAL-config-view-as-book.md v3.7.x (book renderer, MenuAction token model, MenuTokenRegistry TTL conventions) - PROPOSAL-admin-panel.md v2 (curated MenuModel builders; OpenAdminPanel / OpenFrontPage sealed-record variants; permission self-hide pattern) - METRICS_PLAN.md > /rtp info Surface (B11 / C3 / F7) — what gets rendered today Related ADRs: ADR-035 (book/menu architecture), ADR-045 (token registry + TTL), ADR-020 (locale baseline)

    1. Problem statement¶

    /rtp info (canonical: InfoCmd in rtp-core/.../commands/info/) currently emits ~20-40 lines of chat — header, per-world rows, per-region rows, Health — pipeline group, Health — cache (Folia), and the disclaimer block. This is functional for console operators but, in chat, it:

    1. Scrolls past quickly, especially mid-game with combat / world messages interleaved.
    2. Is non-interactive: world / region rows are click-to-suggest (/rtp info world:<x>) but the operator still has to re-type /rtp info to re-read the live numbers.
    3. Is a snapshot. Metrics that move tick-to-tick (TPS, MSPT, queue depth, pending teleports, avg pipeline ms, heap) are frozen at issue time.

    The user (issue: "can we pull the 'info' into book form and later do periodic updates?") asks for a richer presentation: a book MenuModel with the same content, and a refresh affordance so the operator's open book stays current.

    A follow-up update ("maintain optional fallback per book vs text gui choice") requires that the existing chat/text rendering remain selectable, with the choice configurable per-viewer (server default + per-player opt-out).

    2. Goals¶

    • G1. Render /rtp info (no args, world-scoped, and region-scoped) as a MenuModel consumable by the existing BookMenuRenderer.
    • G2. Provide a 🔄 Refresh row inside the book that re-renders the current scope with a fresh MetricsSnapshot.
    • G3. Optionally drive periodic background refreshes for a server-bounded set of open info books (operator dashboards), without re-sending a book every tick.
    • G4. Keep the existing chat/text rendering as a first-class fallback. The choice of book vs text is configurable per-viewer, with a server-wide default.
    • G5. Zero new platform code in rtp-core / rtp-api. All book / chat dispatch stays behind the existing MenuRenderer SPI.

    3. Non-goals¶

    • NG1. Redesigning the content of /rtp info. The metric set, ordering, and locale keys stay byte-identical to today; only the presentation changes.
    • NG2. Multi-page info books in v1. If 14 lines is exceeded, the existing chat block is the source of truth and the book renders a more in chat --> footer that runs /rtp info text-mode.
    • NG3. Console operators getting a book. Console always uses text mode (no Player object to send a book to).
    • NG4. A new permission node. rtp.info remains the only gate.

    4. Proposed design¶

    4.1 Per-viewer rendering preference¶

    New config key under config.yml:

    # How /rtp info renders to players. Console always gets text.
#   auto - book if the player's platform supports books (Paper/Folia
#          with BookMenuRenderer), else text.
#   book - book everywhere a renderer is available; text otherwise.
#   text - always text (legacy behaviour).
infoRenderMode: auto

    Per-viewer override stored alongside other player prefs (same persistence layer used for rtp.personalqueue-style opt-ins; nullable infoRenderMode column in the existing player-prefs accessor — exact name Q1). A new player-facing toggle command /rtp info mode:<auto|book|text> flips the preference and persists it.

    4.2 Dispatch path¶

    InfoCmd.onCommandInner decides up-front:

    mode = effectiveInfoMode(callerId)        // viewer pref -> server default -> auto
if (mode == TEXT || callerId == serverId || !MenuRendererRegistry.hasBookRenderer())
    -> existing text path (unchanged byte-for-byte)
else
    -> new InfoBookBuilder.build(callerId, scopeWorld, scopeRegion).render()

    MenuRendererRegistry is the existing SPI lookup used by MenuRedeemSubcommand.dispatchOpenFrontPage. No new SPI is added.

    4.3 InfoBookBuilder (new, rtp-core)¶

    Sibling to AdminPanelBuilder and FrontPageBuilder. Pure model builder, no platform imports.

    class InfoBookBuilder {
  static MenuModel build(UUID viewer, InfoScope scope, MetricsSnapshot snap, ...);
}

sealed interface InfoScope {
  record Global() implements InfoScope {}
  record OneWorld(String worldName) implements InfoScope {}
  record OneRegion(String regionName) implements InfoScope {}
}

    Rendering rules (all rows self-hide on empty locale value, mirroring the existing text path's "skip if empty" pattern):

    • Title row — infoTitle (already exists).
    • Section: World(s) — infoWorldHeader; one infoWorld row per RTPWorld, click-to-open scope OneWorld. In OneWorld scope, render infoWorldDetail (existing world-info list).
    • Section: Region(s) — infoRegionHeader; one infoRegion row per region, click-to-open scope OneRegion. In OneRegion: region-info list.
    • Section: Health — pipeline — infoHealthPipelineHeader + infoTps, infoMSPTLive, infoSoftCap, infoQueueDepth, infoPendingTeleports, infoAvgPipelineMs, infoHeap, infoDatabaseLatencyMs. (Unchanged keys; just laid out as book rows.)
    • Section: Health — cache (Folia only) — infoFoliaRegionsHeader + repeated infoFoliaRegion rows (B11/C3 work).
    • Section: Footer — 🔄 Refresh row (new key infoBookRefreshRow / hover infoBookRefreshHover), 📜 Switch to chat row (new keys), ↩ Back (only if entered from OpenAdminPanel — uses existing OpenFrontPage semantics... Q2: is /rtp info reachable from the admin panel today, or only via the slash command? If only via slash, the Back row is omitted in v1).

    4.4 Two new MenuAction variants (rtp-api)¶

    Following the OpenAdminPanel / OpenFrontPage shape (no-payload or single-string-payload sealed records, no defensive copies, full equals/hashCode/toString):

    • MenuAction.OpenInfo(InfoScopeToken scope) — opens (or re-opens) the info book at a given scope.
    • InfoScopeToken is a small enum-or-record carrying kind ∈ {GLOBAL, WORLD, REGION} + optional String name.
    • Used by the in-book click rows (World X -->, Region Y -->, 🔄 Refresh).
    • MenuAction.SwitchInfoToText — runs the text path for the same scope and does not mint a new book token.
    • Used by the 📜 Switch to chat row.
    • Also flips the viewer's infoRenderMode to text for this session only (does not persist; persistence requires the explicit toggle command).

    MenuModelSurfaceTest's permitted-types list grows by these two.

    4.5 Redeem path (MenuRedeemSubcommand)¶

    Two new arms:

    • dispatchOpenInfo(senderId, scope, messageMethod) — gated on rtp.info. Builds via InfoBookBuilder, mints token (TTL: 5 minutes — shorter than admin panel's 1h because the data is live and stale tokens would mislead), sends book.
    • dispatchSwitchInfoToText(senderId, scope, messageMethod) — gated on rtp.info. Calls the legacy text path directly with the captured scope; sets the in-memory session pref to text.

    4.6 Periodic refresh (G3)¶

    Two layers, both opt-in and bounded:

    Layer A — manual refresh (always available). The 🔄 Refresh row in any open info book mints a new token at the same scope. Existing TTL semantics handle cleanup.

    Layer B — background auto-refresh (opt-in, capped). New config block:

    infoBookAutoRefresh:
  enabled: false                # default off; this is a dashboard affordance
  intervalSeconds: 10           # min 5, max 300
  maxConcurrentSubscribers: 8   # safety cap; LRU evicts older subscribers
  permission: rtp.info.autorefresh

    When enabled and the viewer has rtp.info.autorefresh:

    • Opening an info book registers the viewer in InfoBookAutoRefreshRegistry (new, rtp-core, keyed by UUID + scope).
    • A single platform-async task (Folia: Global Region Scheduler async; Paper/Spigot: async scheduler; per S-005 hard rules) ticks every intervalSeconds and:
    • Captures one MetricsSnapshot (shared across all subscribers — not one per).
    • For each subscriber whose previous book token is still valid, mints a refreshed token at the same scope and re-sends the book.
    • Drops subscribers whose token has expired (operator closed the book), is offline, or has lost the permission.
    • Subscribers older than the LRU cap are evicted (with a one-time chat notice: "info book auto-refresh: capacity reached, evicting oldest viewer").
    • Logout closes the subscription via the existing player-quit hook.

    Why not push-on-metric-change? That would create chat-spam under load (the entire point is to see movement under load). A bounded interval gives operators predictable refresh cadence without saturating the network.

    S-rule compliance: - S-005: No chunk I/O. The refresh task only reads MetricsSnapshot (already non-blocking) and dispatches book sends through the existing async-safe BookMenuRenderer path. - S-004: A failed refresh (renderer absent, player offline, snapshot null) logs at WARN and silently drops the subscriber — not silently no-ops the whole task. - S-006: API entry points (InfoBookAutoRefreshRegistry.subscribe) throw IllegalStateException if called before core loads.

    4.7 Locale impact¶

    New baseline keys (all via the Locale Config TSV Pipeline):

    • infoBookRefreshRow / infoBookRefreshHover
    • infoBookSwitchToTextRow / infoBookSwitchToTextHover
    • infoBookAutoRefreshNotice (chat-side notice when subscription evicted)
    • infoRenderModeChanged (chat acknowledgement of /rtp info mode:<x>)
    • infoBookOverflowFooter (the more in chat --> row when content exceeds the book cap)

    Total: 5 new key pairs (~9 keys). No removals. Reuses existing infoTitle, infoWorldHeader, infoRegionHeader, infoHealthPipelineHeader, infoFoliaRegionsHeader, and the per-row metric keys verbatim.

    5. Risks and trade-offs¶

    • R1. Snapshot semantics across refreshes. Each refresh captures one MetricsSnapshot, so a single book view is internally consistent (per PlaceholderProvider.withSnapshot). Across refreshes, numbers will jitter — that's the point, but the operator must understand the timestamp. Mitigation: include a last-refreshed: <hh:mm:ss> line in the book footer.
    • R2. Auto-refresh + crowded operator base. A 32-operator server with all subscribed at 5s would mint ~6 book tokens/s and re-send ~6 books/s. The LRU cap (maxConcurrentSubscribers: 8) bounds this. Default enabled: false makes it strictly opt-in.
    • R3. Locale drift. New baseline keys ship with English values across all 12 locales until translated. Per Locale Parity Maintenance rule 4, that's acceptable for v1 with # TODO(i18n): placeholders.
    • R4. Book-cap overflow on OneWorld / OneRegion scopes. A heavily-configured region's region-info list can exceed 14 lines. Fall back to infoBookOverflowFooter row that runs /rtp info region:<r> in text mode. No data loss.
    • R5. Persistence of infoRenderMode. Adding a column to the player-prefs accessor crosses a DB-migration boundary. Q1 below.

    6. Alternatives considered¶

    • A1. Always book, no text fallback. Rejected by the user's update ("optional fallback per book vs text gui choice").
    • A2. Server-wide mode only (no per-viewer override). Simpler, but operators on the same server have different preferences (some want chat for Ctrl+F history searches). Rejected.
    • A3. Push-based refresh on MetricsSnapshot mutation. Rejected per §4.6 (chat-spam under load).
    • A4. Generic "/menu info" entry from the admin panel. Possible later — depends on Q2. Not blocking for v1.

    7. Open questions¶

    • Q1. Persistence layer for infoRenderMode viewer pref: extend the existing player-prefs accessor (DB migration), or treat it as session-only (in-memory map, lost on restart, no DB cost)? I lean session-only for v1 + a roadmap note to promote to persistent if requested.
    • Q2. Should /rtp info be reachable from the admin panel (Diagnostics section), in addition to the slash command? If yes, the admin-panel row dispatches OpenInfo(Global) and the info book grows a Back -> OpenAdminPanel row (otherwise the Back row is omitted). I lean yes, add a Server info (book) row and supersede the existing admin-panel Server info row that currently runs the text command.
    • Q3. Auto-refresh cadence default: 10s, 15s, or 30s? I lean 15s — long enough that operators don't perceive churn, short enough that a TPS dip is visible.
    • Q4. Should the per-viewer toggle be /rtp info mode:<x> (parameter-style, current convention) or a dedicated /rtp prefs info <x> (gestures toward a future rtp.prefs umbrella)? I lean the former for v1 to avoid a new command tree.
    • Q5. When the auto-refresh task evicts a subscriber, should we also auto-resubscribe them next time they open /rtp info, or require them to re-opt-in? I lean auto-resubscribe (LRU-eviction is "you're not at the front of the queue", not "you opted out").
    • Q6. Should infoRenderMode: auto prompt the player the first time (chat hint: "tip: /rtp info now opens as a book; run /rtp info mode:text to keep chat"), or silently use the new default? I lean silent — chat hints become noise.
    • Q7. Token TTL for info-book tokens: 5 min (my draft), or shorter (e.g. 60s) given the data is live? I lean 5 min — refresh is a click, not a re-issue; expiring the click target faster doesn't help anyone.

    8. Implementation order (on approval)¶

    Mirrors PROPOSAL-admin-panel.md v2 §8 structure. Each step is independently verifiable; promote to docs/dev/scratch/CHECKLIST-info-as-book.md per Checklist-Based State Tracking.

    1. MenuAction.OpenInfo + SwitchInfoToText + InfoScopeToken (rtp-api) + MenuModelSurfaceTest rows.
    2. InfoBookBuilder + InfoBookBuilderTest (rtp-core, pure model assertions; no platform).
    3. InfoRenderMode enum + effectiveInfoMode(UUID) + session-pref store (rtp-core).
    4. InfoCmd branch — text path verbatim under mode == TEXT || console || no-renderer, book path otherwise. Tests assert the text path is byte-identical to today on mode=text.
    5. MenuRedeemSubcommand — dispatchOpenInfo, dispatchSwitchInfoToText, new SAM, permission gate on rtp.info.
    6. BookMenuRenderer.toClickEvent two new arms + BookMenuRendererTest round-trips.
    7. InfoBookAutoRefreshRegistry (rtp-core) + scheduled task wiring per platform; default disabled; LRU + permission gate. New ReqRtpInfoBookAutoRefreshBoundedTest covers the LRU cap and S-004 failure paths.
    8. Locale TSV pipeline pass: 5 new key pairs (~9 keys); no removals.
    9. /rtp info mode:<auto|book|text> parameter wiring under InfoCmd's existing parameter lookup; persistence per Q1 outcome.
    10. CHANGELOG.md bullet (absolute terms vs v3.0.0-beta.2).
    11. LocaleParityTest + scoped tests + .\gradlew build (mandatory final full build).

    9. Notes¶

    • Em / en dashes not introduced (per AGENTS.md Markdown Encoding Hygiene rule 7); ASCII punctuation throughout.
    • This proposal is purely additive within ADR-035 / ADR-045; no superseding ADR is anticipated.
    • Auto-refresh (G3) is the highest-risk piece. If Q3/Q5 reveal disagreement, ship v1 without auto-refresh — manual 🔄 Refresh alone covers the user's "later do periodic updates" intent at acceptable cost — and defer auto-refresh to v2.
