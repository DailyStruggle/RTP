    Modrinth Listing Optimization - Working Notes¶

    Status: scratch / working notes (gitignored under docs/dev/scratch/). Source conversation: 2026-05-19, migration from SpigotMC to Modrinth. Author: drafted by Junie at user request; not canonical until promoted to docs/marketing/ or an ADR.

    This document distills the six Gemini-suggested marketing tactics into a repo-specific action plan. Each item is filtered against what actually exists in this codebase (modules, ADRs, build pipeline) so the recommendations are concrete, not generic.

    TL;DR ranking (by return-on-effort)¶

    1. Automated Modrinth releases via GitHub Actions (point 4) - recurring downloads, zero ongoing cost.
    2. Modrinth README rewrite emphasizing architecture + diagrams (points 1 + 2) - one-time write, biggest first-impression delta.
    3. SpigotMC funnel banner edit (point 5) - 10-minute edit to two .bbcode files.
    4. Support-expectations section on the Modrinth page (point 3) - short, sets SLA boundaries.
    5. Hold the platform-compatibility claims to what is actually stable (point 6) - Fabric stays off the supported list until Phase 4 closes.

    1. Market the technical architecture¶

    Verdict¶

    Correct direction. Modrinth's audience skews toward Paper/Folia admins who read READMEs and care about MSPT. The differentiators in this repo are real, not marketing fluff:

    • Archimedean spiral 1D mapping - ADR-001. Bounded worst-case attempts, O(1) coordinate generation, no unbounded reroll loop.
    • L1 / L2 / L3 cache tiering (keptLocations / unkeptLocations / backlogLocations) - ADR-028. Most competitors pick on-demand.
    • Anvil NBT pre-filter - ADR-016. Biome/material checks without loading chunks.
    • Count-bound pipeline on Folia (vs Time-Bound on Spigot/Paper) - preserves region-thread budgets.
    • MemoryTracker lifecycle for chunk tickets and pipeline tasks - release on every exit path (S-002).
    • Zero synchronous chunk I/O on the main thread (S-005) verified by ReqRtpS005ChunkLoadingTest and related guards.

    Caveat¶

    Do not trash "legacy plugins with quadtrees." That tone reads as marketing on a technical audience and invites pedantic rebuttals. State the trade-off honestly instead - the spiral is not strictly faster than a quadtree for every query, it is a different shape of trade-off (bounded distribution, cheap 1D index, no rejection sampling).

    Concrete next step¶

    Draft docs/marketing/MODRINTH_README.md distilled from docs/dev/CONCEPTS.md plus ADR-001 / ADR-016 / ADR-028. Audience: admins evaluating in under 60 seconds, not contributors.

    Sketch outline:

    1. One-line value prop ("Async-only random teleport for Paper, Folia, and Bukkit, with pre-verified location cache and bounded spiral coverage").
    2. Bullet list of measurable claims (no synchronous chunk loads; pre-verified pool; count-bound on Folia).
    3. Three-image gallery (see point 2).
    4. Config sample (the simplest possible).
    5. Links to deep docs (docs/dev/INDEX.md) for the technical reader.
    6. Support expectations (see point 3).

    2. Visual documentation¶

    Verdict¶

    Agree. Low cost, high payoff. Modrinth renders embedded images from the project gallery and from raw GitHub URLs.

    Assets to produce¶

    • Spiral coverage plot (uniform distribution over a bounded annulus). The repo already has Python Test Scripts/Circle Curve/ which presumably emits something close.
    • Pipeline diagram (shape -> chunk -> vert -> biome -> safety) annotated with which stages are async on which platform.
    • Cache-tier diagram (L1 hot / L2 cold / L3 backlog) - translates ADR-028 into something an admin grasps in one look.

    Static PNGs only. No animated SVGs, no clever interactive widgets.

    Concrete next step¶

    docs/marketing/img/ directory, three PNGs, referenced by relative path from the future Modrinth README and by raw-GitHub URL from the Modrinth listing.

    3. Optional support funnel¶

    Verdict¶

    Agree on the principle (set expectations explicitly), disagree that a Discord is required. GitHub Issues already exists, SUPPORT.md already exists.

    What is missing is a one-paragraph "how to report a bug" on the Modrinth page itself with explicit "best-effort, no SLA" language. The Discord-vs-no-Discord question is a personal-bandwidth decision, not a strategic one - adding a Discord obligates moderation.

    Do not link from the Modrinth page¶

    • docs/dev/POTENTIAL_BUGS.md - internal stay-on-task policy, not user-facing.
    • .junie/AGENTS.md - internal contributor / agent contract.

    Do link¶

    • SUPPORT.md
    • CHANGELOG.md
    • docs/dev/INDEX.md (signals seriousness to technical evaluators without writing fresh marketing copy)

    Known-limitations section¶

    Worth being upfront about. Per docs/dev/MULTI_PLATFORM_PLAN.md:

    • Fabric (rtp-fabric) is the current frontier and unstable; do not claim Fabric support on the Modrinth page yet (see point 6).
    • Forge / NeoForge: out of scope until Fabric stabilizes (Phase 4).
    • Velocity / BungeeCord: planned via rtp-proxy per ADR-036, Phase 1 unblocked, not yet user-installable.

    4. Strategic update cadence¶

    Verdict¶

    Highest-ROI item on the list. Aligns with how Modrinth's discovery works (Recently Updated feed, follower notifications). The blocker is not tooling; the discipline already exists:

    • CHANGELOG Hygiene rule in .junie/AGENTS.md enforces net-delta-from-released-tag - exactly the hygiene that makes frequent releases safe.
    • Jenkinsfile already builds; adding a GitHub Actions release path does not displace it.
    • The lite-assembly variant (ADR-024) gives two artifacts per release - more surface area on the Modrinth page.

    Concrete next step¶

    .github/workflows/release.yml triggered on v* tag push:

    1. Run .\gradlew build (full multi-module, per the AGENTS.md Final Full Build rule).
    2. Upload main jar and lite jar via modrinth/minotaur@v2.
    3. Pull the matching CHANGELOG section as the Modrinth release notes (already in net-delta form, so this is correct by construction).
    4. Tag the Modrinth release with the loaders the build actually supports (paper, folia, bukkit; not fabric - see point 6) and the MC versions matching rtp-bukkit-v* / rtp-paper-v* / rtp-folia-v* submodules.

    Secrets required: MODRINTH_TOKEN. Out of scope for this scratch doc to author the workflow - captured here as the next deliverable.

    Release cadence policy (proposed)¶

    • Patch / beta releases on every meaningful bugfix or single-issue change that passes the full build.
    • Minor releases when a feature lands behind a config flag.
    • Major releases reserved for breaking API changes (rtp-api surface) - these need release notes plus a migration paragraph.

    Avoid the "save up features for a big release" anti-pattern Gemini called out. The CHANGELOG hygiene already supports small-frequent.

    5. Funnel from SpigotMC¶

    Verdict¶

    Agree tactically. SEO point is real: SpigotMC outranks Modrinth for legacy queries, and the existing docs/FRONT_PAGE.bbcode plus docs/FRONT_PAGE_LITE.bbcode are ready to retarget.

    Do¶

    • Add a prominent banner at the top of both .bbcode files: "Latest builds, Folia tags, and beta channels live on Modrinth: ." Keep the language welcoming, not aggressive.
    • Keep the latest stable on Spigot so existing users do not lose access.
    • Push betas, Folia-tagged builds, and the lite variant to Modrinth only. That asymmetry is the natural funnel - people who want the new thing learn where to look.

    Do not¶

    • Fully cripple Spigot downloads. That creates support load from confused users who cannot find anything and damages reputation.
    • Edit FRONT_PAGE.bbcode while also changing semantic content; keep the funnel edit isolated for an auditable diff.

    Concrete next step¶

    Two-file edit, ~10 minutes, low risk:

    • docs/FRONT_PAGE.bbcode
    • docs/FRONT_PAGE_LITE.bbcode

    Both files are user-facing marketing copy; per .junie/AGENTS.md Markdown Encoding Hygiene, use ASCII punctuation (no em dashes) and verify no mojibake before submit.

    6. Broaden ecosystem compatibility¶

    Verdict¶

    Already in progress; do not over-promise. Current state per repo:

    • Bukkit / Paper / Folia: first-class, all green.
    • Fabric (rtp-fabric): active frontier, unstable. Known blockers per MULTI_PLATFORM_PLAN.md:
    • S-005 violation in FabricWorld.getChunkAt.
    • Null stub in FabricServerAccessor.getLocationGenerator.
    • Unresolved Loom dependency.
    • Velocity / BungeeCord: Phase 0 complete (ADR-036), Phase 1 unblocked, no user-installable artifact yet.
    • Forge / NeoForge: out of scope until Fabric stabilizes (Phase 4).

    Pterodactyl auto-pull¶

    Real lever and worth optimising for. Pterodactyl eggs query Modrinth's API by project_id and resolve the latest version matching the egg's declared loader and MC version. Implication: the more accurate the loader / MC-version tags on each Modrinth release, the more automated installs happen. This is purely a tagging discipline question, not a code question.

    Do not¶

    • List Fabric as "supported" on the Modrinth page until Phase 4 closes. Listing an unstable platform damages exactly the technical-admin reputation that point 1 is trying to build.
    • Mirror the rtp-proxy artifacts to Modrinth before Phase 1+ is user-installable. Mark them as planned only.

    Items Gemini did not surface that matter more¶

    • Modrinth loader / version tags are the actual discoverability lever. Tag every release with the exact MC versions and loaders. Admins filter the project search by these; the README is secondary.
    • The lite jar is a marketing asset, not just a technical one. "Drop-in, no config, small footprint" framing on Modrinth captures a different audience than the full feature set. Make the lite jar a separate "version" on the Modrinth project rather than a buried download.
    • The existing docs/dev/ tree is a moat. It is unusually thorough for a Minecraft plugin. A one-line "Full developer documentation: " on the Modrinth page signals seriousness to the admin demographic point 1 targets, with zero new writing.
    • Locale parity is a quiet selling point. The locale TSV pipeline and LocaleParityTest guarantee that shipped locales never silently fall back to English - worth one bullet on the Modrinth page for international audiences ("ships with N locales, parity-enforced").
    • Don't gate on a Modrinth project description rewrite. The Modrinth README and the GitHub README can stay separate. The GitHub README is for contributors; the Modrinth README is for admins. Tailor each to its audience.

    Open questions for the user¶

    1. Discord channel: create one or not? Defaults to "not" unless the user wants the moderation load.
    2. Modrinth project URL / slug already reserved?
    3. Who holds the MODRINTH_TOKEN and is willing to add it as a GitHub Actions secret?
    4. Spigot resource: keep it active indefinitely, or sunset after N releases on Modrinth?
    5. Do we want the lite jar promoted as a "version" on the same Modrinth project, or its own project?
