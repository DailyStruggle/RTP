    Plan: unify the /rtp menu-binding SPI across all platforms¶

    Effective Issue: "I want platform implementations to look similar and complete the same SPI so we can cut back on unnecessary separate code paths." Approved direction (2026-06-21): rtp-core owns menu discovery+selection; every platform completes MenuRendererProvider/AnvilInputOpenerProvider via META-INF/services; the three roots collapse to no-arg shells.

    Mode: [CODE] (D-005 — crosses rtp-core + rtp-api + all three platform adapters). Plan written first, awaiting go before coding.

    Decision (resolved): No "chat" renderer id provider. Chat renderer is extraneous for menus and a removal target; register book only on every platform (the book renderer's internal ChatMenuRenderer fallback for 1.20.x stays as-is).

    Background — what diverges today¶

    • All three roots already extends CoreRtpRoot (ADR-070). Structural skeleton identical.
    • The ONLY divergent code path is how the menu renderer + anvil/chat-prompt opener are supplied:
    • Bukkit: BukkitMenuBindings.selectMenuRenderer() / selectAnvilOpener() discover via ServiceLoader against MenuRendererProvider (rtp-api) + AnvilInputOpenerProvider (rtp-core), select renderer by the menu.renderer config id, pass results to the CoreRtpRoot(menuRenderer, anvilOpener, replyRenderer) ctor. Paper adapter ships the two providers + service files.
    • Fabric: RTPCmdFabricRoot() hard-codes new FabricBookMenuRenderer(new ChatMenuRenderer()) + new FabricChatPromptCallback(). Ignores menu.renderer config; does not touch the SPI.
    • NeoForge: same shape with NeoForgeBookMenuRenderer + NeoForgeChatPromptCallback.
    • Live behavior gap: menu.renderer: [] / a non-book id is honored on Bukkit, silently ignored on Fabric/NeoForge.

    Target end state¶

    • One neutral discovery+selection path in rtp-core, used by every platform.
    • Each platform adapter ships provider classes + META-INF/services files completing the identical two SPIs.
    • Roots become no-arg (Fabric/NeoForge) / reply-renderer-only (Bukkit) shells; no platform names a renderer/opener class in its root.

    Design¶

    1. New rtp-core selection helper¶

    io.github.dailystruggle.rtp.common.commands.menu.MenuBindingSupport (rtp-core), holding the logic lifted verbatim from BukkitMenuBindings: - static @Nullable MenuRenderer discoverRenderer() — read menu.renderer config id list (default [book], empty list = no renderer), ServiceLoader.load(MenuRendererProvider.class, <cl>) keyed by id(), first-matching-config-id wins, WARNING+skip on unknown/throwing ids. - static @Nullable MenuRedeemSubcommand.AnvilInputOpener discoverAnvilOpener() — first discoverable AnvilInputOpenerProvider, null-tolerant. - Classloader: use MenuRendererProvider.class.getClassLoader() (matches current Bukkit behavior; everything shaded into one jar on Bukkit, single module classloader on Fabric/NeoForge). Note risk below.

    2. CoreRtpRoot constructors¶

    • Keep the existing explicit-injection ctor CoreRtpRoot(MenuRenderer, AnvilInputOpener, replyRenderer) (used by CoreCommandTreeBuilderTest / direct tests) — internal/back-compat.
    • Add CoreRtpRoot() → self-discovers via MenuBindingSupport, replyRenderer = null. (Fabric/NeoForge)
    • Add CoreRtpRoot(Function<UUID,Consumer<String>> replyRenderer) → self-discovers menu, custom reply renderer. (Bukkit help-row clickable chat)

    3. Platform providers + service files¶

    • Bukkit/Paper: already done (PaperBookMenuRendererProvider, PaperAnvilInputOpenerProvider + 2 service files). No change beyond the bootstrap call site.
    • Fabric (rtp-fabric-common): add
    • FabricBookMenuRendererProvider implements MenuRendererProvider → id()="book", create()=new FabricBookMenuRenderer(new ChatMenuRenderer()).
    • FabricAnvilInputOpenerProvider implements AnvilInputOpenerProvider → create()=new FabricChatPromptCallback() (self-registers its listener).
    • META-INF/services/io.github.dailystruggle.rtp.api.menu.MenuRendererProvider (both renderer providers) and ...AnvilInputOpenerProvider.
    • NeoForge (rtp-neoforge-common): symmetric set (NeoForge...Provider x2 + 2 service files).

    4. Root + bootstrap collapse¶

    • RTPCmdFabricRoot / RTPCmdNeoForgeRoot → empty body, super() (kept only to give the Brigadier bridge a named CommandsAPICommand; document why).
    • BootstrapSupport: build new CoreRtpRoot(new BukkitHelpReplyRenderer()); delete the BukkitMenuBindings.selectMenuRenderer()/selectAnvilOpener() calls. BukkitMenuBindings is then either deleted (logic moved to rtp-core) or reduced to nothing — prefer delete, since its sole purpose was the now-shared selection.
    • BukkitTestCmd + event-seam subscription stay at the Bukkit bootstrap (Bukkit-only) — unchanged.

    Risks / trade-offs¶

    • ServiceLoader now runs in rtp-core for everyone (trivial indirection over a direct new for Fabric/NeoForge) — accepted price for one code path.
    • Service-file merge in shaded/remapped jars: must confirm Fabric (Loom) and NeoForge (ModDevGradle) keep META-INF/services entries intact in the final mod jar (Bukkit already uses mergeServiceFiles in shadow). Verify during build; if a relocation/merge strips them, add the equivalent merge step.
    • Classloader for ServiceLoader on Fabric/NeoForge: confirm the adapter's providers are visible from MenuRendererProvider.class.getClassLoader(); if mod isolation interferes, fall back to Thread.currentThread().getContextClassLoader() or the root instance's classloader.
    • No verb/tree/permission/order change — command tree stays byte-for-byte identical; only menu-binding plumbing changes.

    Scope guardrails¶

    • No verb add/rename/move; no messages.yml/lang/TSV/CHANGELOG verb edits.
    • effects-api untouched.
    • menuInvalid null-tolerant degradation preserved exactly.

    Verification¶

    • rtp-plugin command tests (80) green; rtp-core CoreCommandTreeBuilderTest (2) + RTPCommandEventsTest (3) green.
    • Add a focused rtp-core test for MenuBindingSupport discovery/selection (config-id pick, empty-list = null, unknown-id skip) with a stub provider on the test classpath.
    • Final full ./gradlew build (multi-module — exercises Fabric + NeoForge service-file packaging).

    Docs¶

    • Amend ADR-070 to describe the symmetric end state (all three platforms complete the same SPI; rtp-core owns selection); update commands-api-ADR-003 cross-ref if needed.
