    Proposal: De-canonicalize CommandsAPI.parameterDelimiter after the : -> = migration¶

    Status: draft (awaiting D-005 approval) Origin: chat 2026-05-20, follow-up to the command-syntax migration from : to =.

    Context¶

    With : retired as the parameter delimiter, the configurability layer in commands-api is dead weight: the character is no longer data, it is a fixed grammar token. The codebase still pays the cost of an abstraction whose only historical purpose was to let the delimiter vary.

    What's currently in the way¶

    • CommandsAPI.parameterDelimiter is a mutable public static char = '='. Mirror field: multiParameterDelimiter = ','.
    • ~20 call sites in commands-api/.../TreeCommand.java use String.valueOf(CommandsAPI.parameterDelimiter) to feed split / contains / indexOf / lastIndexOf.
    • Three helpers (containsParamDelimiter, indexOfParamDelimiter, splitOnParamDelimiter) wrap one-line String.indexOf('=') calls.
    • BukkitValueCoercer.legacyColorFromDelimitedString is @SuppressWarnings("unused") and self-describes as the legacy path.
    • REQ-API-F-005 is still phrased as if the delimiter were configurable.

    Proposal (phased)¶

    Phase 1 - safe, mechanical, single PR. No public API removal.

    • Make parameterDelimiter and multiParameterDelimiter public static final.
    • Inside commands-api itself, replace String.valueOf(CommandsAPI.parameterDelimiter) with "=" literals at the ~20 sites; prefer char overloads of indexOf / split where the API permits.
    • Inline containsParamDelimiter and indexOfParamDelimiter. Keep splitOnParamDelimiter as the one named grammar primitive.
    • Delete BukkitValueCoercer.legacyColorFromDelimitedString.
    • Re-word REQ-API-F-005 to absolute state: "The parameter delimiter shall be =."
    • Affected modules: commands-api, effects-api. No rtp-core changes.
    • Cross-module callers (effects-api etc.) keep the named-constant reference (cheap, documents intent).

    Phase 2 - only after Phase 1 lands and an addon survey confirms no consumers.

    • @Deprecated(forRemoval=true) on parameterDelimiter / multiParameterDelimiter, with Javadoc pointing to the literal.
    • Hold one major.

    Phase 3 - defer to next major.

    • Remove the fields entirely.

    Risks / trade-offs¶

    • Addon binary compat. parameterDelimiter is on the public commands-api surface and read transitively via effects-api. final is safe; removal is not.
    • Locale / messages.yml strings. BaseRTPCmd already builds parameterName + "=" + parameterValue. Sweep user-facing help strings for any residual name:value framing before merging.
    • Traceability. REQ-API-F-005 row in TRACEABILITY.md needs a re-check when the requirement text moves.
    • Don't over-rotate. A static final char PARAM_DELIMITER = '='; is still a useful named constant (for the Brigadier bridge and for grep-ability). The thing worth deleting is the configurability, not the name.

    Verification plan¶

    • :commands-api:test, :rtp-core:test, :rtp-plugin:test --tests "*Tree*", full .\gradlew build.
    • Brigadier suggestion smoke (tab-complete still appends =).
    • LocaleParityTest (no message-text drift).

    Out of scope¶

    • The reg: value-side sigil in TreeCommand.expandRegexToken. That is a sub-token marker inside the value half, not a separator, and the freed : is actually one of the upsides of the migration.
    • minecraft:-prefix stripping in BukkitValueCoercer.resolveViaRegistry / resolveSound. Tracked as a separate decanonicalization opportunity (see follow-up chat 2026-05-20).
