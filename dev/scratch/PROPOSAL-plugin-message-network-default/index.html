    PROPOSAL - Plugin-Message Network Transport as the Default Tier (DB-free cross-server RTP, proxy auto-detect, lite-shipped)¶

    Status: Approved (design-only; no code in scope; D-005 gate cleared 2026-06-12 by repo owner leaf) Date: 2026-06-12 Owner: leaf (repo owner) Effective Issue: give the free/lite edition a competitive cross-server RTP story against EzRTP without sacrificing the large-network optimizations (durable reservation tokens, atomic claims, load-balanced selection) that justify the Pro Redis/SQL tiers. Make a plugin-messaging transport the default so that a database is not required for most operators, and auto-detect the proxy so the operator config shrinks to near-nothing. Refines: MULTI_SERVER_PLAN.md (plugin-message transport currently "dev-only", D2); ADR-024 (lite assembly scope); ADR-036 (network-mode umbrella); rtp-proxy-ADR-* transport-binding family. Reuses (no SPI changes): NetworkTransport, BackendHeartbeat, NetworkSnapshot, BackendSelector in rtp-proxy-common.

    1. Thesis¶

    EzRTP's "network" feature is a backend-only server selector: a static, hand-maintained servers: list per backend, online/offline detected by direct host:port server-list pings, and player movement performed by speaking the proxy's built-in plugin-messaging vocabulary (Connect) over the issuing player's connection. It needs no proxy plugin and no database. Its ceiling: it transmits only server up/down, never which regions/worlds are servable, and the server list drifts because every backend is configured by hand.

    We can match its zero-infra baseline and beat its capability by shipping a PluginMessageNetworkBinding that implements the existing NetworkTransport SPI over the proxy's plugin-messaging channel, carrying our richer BackendHeartbeat (region availability, warm-cache counts, load) instead of a bare ping. Backends self-advertise, so the network assembles itself with no hand-typed server list.

    This is purely an additive transport tier. The durable Pro tiers (RedisNetworkStateBinding, SqlNetworkStateBinding) remain unchanged behind the same SPI; the dispatcher, selector, and command/tab-complete layer do not know which transport is underneath.

    2. Transport tiers (one SPI, four implementations)¶

    Tier NetworkTransport impl Availability source Reservation / atomic claim Durable Edition
    0 InMemoryNetworkStateBinding (existing) in-JVM yes (in-JVM) no dev/test
    1 (new default) PluginMessageNetworkBinding BackendHeartbeat relayed via proxy Forward sub-channel best-effort / none (player re-issues on miss) no lite + Pro
    2 SqlNetworkStateBinding (existing) DB UPSERT + poll (Postgres LISTEN/NOTIFY) yes yes Pro
    3 RedisNetworkStateBinding (existing) pub/sub yes (atomic Lua + HMAC token) yes Pro

    MySQL is the free durable tier (tier 2); Postgres is the higher-performance tier-2 variant via LISTEN/NOTIFY. Redis (tier 3) is the lowest-latency, atomic-claim tier.

    Selection precedence in network.yml: explicit transport.type wins; transport.type: auto (the lite default) resolves to tier 1 when a proxy is detected and to "disabled" when standalone.

    3. PluginMessageNetworkBinding shape¶

    Keep as much as possible in rtp-core behind a thin NetworkBridge seam, and only drop down to a platform/proxy adapter at the exact points where the platform plugin-messaging API must be called. This is not Bukkit-specific: a Fabric (or NeoForge) backend fronted by Velocity must reach the same binding, so the message framing, heartbeat assembly, TTL expiry, snapshot maintenance, and the auto state machine all live in rtp-core; only the raw "send these bytes on bungeecord:main over player P's connection" / "receive bytes" primitive is delegated to the adapter (Bukkit#sendPluginMessage, Fabric custom-payload, etc.).

    Backend-side binding (rtp-core NetworkBridge + a small per-platform send/receive shim). Implements NetworkTransport:

    • publishBackendHeartbeat(BackendHeartbeat row) -> serialize the record (already carries serverId, regionsAvailable, worldsLoaded, regions, regionKeptCounts, acceptingRequests, pluginState, killSwitch, keptCount) and emit it on the proxy Forward (or ForwardToPlayer) sub-channel of bungeecord:main, throttled to a heartbeat interval (default 200 ticks, the EzRTP ping-interval-ticks analogue).
    • subscribeBackendHeartbeats(sink) / readSnapshot() -> maintain the last-seen BackendHeartbeat per serverId; expire entries on a TTL (the plugin-message analogue of ping-timeout-millis); invoke sink on change. readSnapshot() returns the assembled NetworkSnapshot.
    • Move: the dispatcher's connect step emits Connect <serverId> (or ConnectOther <player> <serverId>) on the issuing player's connection. The destination backend detects the join and runs a normal local /rtp.
    • claim / redeem / release / reapExpired / findReservation -> best-effort / no-op. There is no durable token store. On a miss (region drained, world unloaded, backend gone), the destination's local pipeline bounces with an S-007 configurable "busy / no such region" message and the player re-issues. This is the same correctness posture EzRTP lives with, but with real region data.

    No rtp-proxy-common SPI surface changes: this is a peer of InMemoryNetworkStateBinding.

    4. Proxy auto-detection (transport.type: auto)¶

    Two layers:

    Layer 1 - passive probe (gate, not source of truth). Read whether proxy forwarding is enabled: - Spigot: settings.bungeecord: true in spigot.yml. - Paper: proxies.bungee-cord / proxies.velocity in paper-global.yml. This arms network mode but supplies neither this backend's proxy name nor the sibling list.

    Layer 2 - active handshake (the real detect + topology learn). Register bungeecord:main always; on the first player join, send: - GetServer -> proxy replies with this backend's own proxy name (operator never hand-types it). - GetServers -> proxy replies with the full backend-name list.

    State machine: UNKNOWN -> (passive probe true) ARMED -> (first join: send handshake) PROBING -> (reply within timeout, default ping-timeout-millis: 1500) ENABLED; else DISABLED (standalone). Heartbeat gossip begins only in ENABLED. Re-probe on proxy reconnect.

    Result: drop the jar on every backend, the network assembles itself - strictly better than EzRTP's static per-server servers: list.

    5. network.yml (lite) shape¶

    Minimal; mirrors EzRTP's servers.<name> vocabulary only where an operator must still express policy a backend cannot self-discover.

    network:
  transport:
    type: auto        # auto | plugin-message | sql | redis | inMemory | disabled
    heartbeatTicks: 200
    staleTimeoutMillis: 1500
  # Optional per-server policy overlay; absent => discovered server is offered with defaults.
  servers:
    skyblock:
      permission: ""           # gate visibility/use of this destination
      display-name: "Skyblock"
      hide-when-unavailable: false
      allow-when-unavailable: false

    There is no hand-typed server list required in auto mode: servers: is an optional policy overlay keyed by the discovered names. host/port are gone (availability is the heartbeat, not a socket ping).

    6. Honest limitations (document loudly; they define the Pro upgrade boundary)¶

    1. Everything rides a player connection. GetServers, Forward, and Connect require an online player on the sending backend. Auto-detect completes only on first join (acceptable). A player-empty backend cannot broadcast its heartbeat, so its availability goes stale/unknown.
    2. Unknown -> accept. isRelevant (execute-time region validation) must accept when the snapshot is unknown/stale and let the destination decide; suggestion filtering may stay strict. Otherwise transport lag becomes user-visible command failures.
    3. Single-proxy fan-out. Forward only reaches backends visible to one proxy. Multi-proxy (RedisBungee-style) networks need tier 2/3 - the clean, honest upgrade boundary.
    4. Non-durable. No reservation survives a proxy restart (D2). Worst case is a re-issued /rtp. Operators needing atomic, durable, load-balanced cross-server reservation move to MySQL/Postgres/Redis.
    5. Optional proxy companion (future). The existing rtp-proxy-velocity / rtp-proxy-bungee plugins can hold the channel open independent of player presence and relay heartbeats reliably - an enhancement, not a baseline requirement.

    7. Tab-completion / validation (cross-server region parameter)¶

    A NetworkRegionParameter whose values() returns the cached availability snapshot for the chosen target server and whose isRelevant validates against the same snapshot with the §6.2 "unknown -> accept" grace. The snapshot provider is pluggable (config overlay / plugin-message / SQL / Redis) so the command layer is transport-agnostic. Pure-config operators (no transport) get a static declared list (EzRTP parity); the heartbeat tiers eliminate the drift.

    8. What this does NOT change¶

    • rtp-proxy-common SPI: zero changes. Tier 1 is a peer implementation.
    • Pro selector / claim / token logic: reused unchanged behind the SPI.
    • ADR-024 lite excludes (SQL drivers, Redis, Folia adapter classes): unchanged. Tier 1 adds no driver; the binding lives in a backend-reachable module and ships in lite. liteJarStructureCheck extended only to assert no Redis/SQL transport class leaks while permitting PluginMessageNetworkBinding.
    • S-00x: the destination always runs the normal local pipeline (spiral -> chunk -> safety), so S-001/S-004/S-005 hold; tier 1 transports intent, not a coordinate. Move failures are logged, never swallowed (S-004); busy/invalid messages are configurable (S-007).

    9. Resolved decisions (formerly open questions)¶

    1. Heartbeat serialization format - RESOLVED: reuse. Forward payloads reuse the existing Redis flat-field encoder (encodeBackend/decodeBackend) over the proxy channel, so tier 1/2/3 share one decoder and the BackendHeartbeat field set is identical across transports. No new wire format.
    2. Module ownership - RESOLVED: maximise rtp-core. The binding lives in rtp-core behind a NetworkBridge seam; only the raw platform plugin-messaging send/receive primitive is delegated to a per-platform shim (see §3). This is deliberately not a Bukkit-only adapter because Fabric/NeoForge backends can also sit behind Velocity. Backend-specific code appears only if/when we depend on the Bungee API directly; BungeeCord support is layered on top of the existing Velocity support later and is not required for this tier.
    3. Heartbeat delivery / cost - RESOLVED: use the proxy as the store. Rather than treating availability as a per-backend database status, the proxy itself is the rendezvous point - backends gossip BackendHeartbeat through it and origins read the last-seen snapshot from it. This is the DB-free analogue of the tier-2/3 status table; throttle stays at the default 200-tick heartbeat interval and is revisited only if chatty at large N.
    4. Velocity channel handling - DECISION: implement if absent. Confirm GetServer/GetServers/Connect/Forward are honored on current Velocity; we do not appear to exercise all of these yet, so any missing piece (notably the modern namespaced-channel registration and the GetServers/topology handshake) is in scope to add.
    5. auto re-probe - RESOLVED: re-probe. A standalone server that later joins a proxy must re-probe live (on first join and on proxy reconnect) rather than requiring a restart.

    9a. Self-pausing backends (Fabric / NeoForge)¶

    Fabric and NeoForge backends are valid proxy targets but self-pause after ~60 s of no player activity (Minecraft's idle-tick pause). Consequences for tier 1:

    • A paused backend stops ticking, so it cannot emit heartbeats and its auto handshake/gossip stalls - its snapshot entry goes stale exactly as the §6.1 player-presence limitation predicts. Treat "stale/unknown" the same as player-empty: unknown -> accept (§6.2), let the move + destination decide.
    • The Connect move still wakes a paused backend (the proxy transfer resumes ticking on player arrival), so cross-server RTP into a paused Fabric/NeoForge backend works; only its advertised availability is unreliable while paused.
    • Do not rely on a paused backend to answer a synchronous availability query. The staleTimeout must tolerate the idle-pause window (default 1500 ms is far shorter than 60 s, so a paused backend is correctly shown stale). Operators wanting always-fresh availability for idle backends are pointed at the durable tier-2/3 store (which survives independent of backend ticking) or the optional proxy companion (§6.5).
