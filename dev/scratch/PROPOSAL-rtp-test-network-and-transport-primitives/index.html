    PROPOSAL: rtp test network (Shape A) + NetworkTransport composes RTPServerAccessor primitives¶

    Status: Proposed, docs-only, awaiting D-005 approval. Author: Junie session 2026-05-18. Scope: two coupled deliverables, see §1.

    1. Why two deliverables in one proposal¶

    The user asked for an automated integration test (rtp test network, Shape A "inject synthetic peers into the live binding"). Standing that up surfaced a question about how a test job in rtp-core reaches the live NetworkTransport on the current JVM, when network mode is enabled.

    Direct answers (RTP.networkTransport static slot, RTPServerAccessor.networkTransport() getter, etc.) were each rejected by the user. The user's chosen direction is:

    "RTPServerAccessor should implement methods that NetworkTransport would rely on instead of NetworkTransport needing multiple implementations" - "if anything is worth doing eventually it's best done immediately here."

    That is a larger architectural reframe of the proxy SPI than what "register a new test subcommand" normally implies. Per Rule D-005 (Propose Before Implementation), the two deliverables are bundled into one proposal so the test job is designed against the same SPI shape we land for production use, not against today's shape that is about to change.

    Deliverables:

    1. Architectural reframe. NetworkTransport becomes one shared implementation per transport type (in-memory, SQL, future Redis), but stops growing per-platform variants. Platform primitives the transport needs (logger, async executor, server id, current monotonic clock) are pulled from RTPServerAccessor (rtp-api) instead of being baked into the transport class.
    2. rtp test network Shape A. A new platform-agnostic test job in rtp-core that publishes N synthetic BackendHeartbeats through the already-live transport, asserts they appear in the local snapshot, asserts subscriber fan-out fires, and cleans up. Registered in TestCmd base so Bukkit + Fabric both get it.

    Both land in one implementing turn, against the new SPI shape from item 1.

    2. What is wrong with the current shape¶

    SqlNetworkStateBinding (Phase 2e-SQL, shipped) is ~475 LOC and contains:

    • JDBC plumbing (UPSERT, atomic claim, snapshot SELECT, poll loop).
    • A self-managed ScheduledExecutorService for the 1s poll loop.
    • A self-managed CopyOnWriteArrayList of subscribers.
    • Hand-rolled clock reads (System.currentTimeMillis()).
    • Hand-rolled logging (uses RTP.log via a static accessor).

    InMemoryNetworkStateBinding separately implements its own:

    • ConcurrentHashMap-backed snapshot.
    • Its own CopyOnWriteArrayList of subscribers.
    • Its own clock reads.
    • Same logging path.

    The two share none of this scaffolding even though it is identical in shape. Adding RedisNetworkStateBinding would duplicate it a third time. Each new platform that wants to host the transport (e.g. eventually Fabric needing its own scheduler hand-off) is forced to either:

    • Subclass / replicate the binding per platform (the current trajectory, explicitly rejected by the user), or
    • Have the binding learn each platform's primitives inline (forbidden by Architecture Boundaries; rtp-proxy-common may not import platform types).

    The user's correction is the natural way out: factor the scaffolding into platform primitives exposed on RTPServerAccessor. The transport calls them; the platform supplies them.

    3. New primitives on RTPServerAccessor¶

    Additive only. All defaulted to the current single-platform behaviour, so existing platform ServerAccessor implementations remain valid until they opt in.

    package io.github.dailystruggle.rtp.api.server;

public interface RTPServerAccessor {

    // ... existing methods (sendMessage, getPlayer, scheduler, log, etc.)

    /**
     * Schedule a periodic task. The transport uses this for its poll loop
     * (SQL) or its TTL reaper (in-memory / Redis). Returns a handle the
     * transport calls to cancel the task on close.
     *
     * Default implementation delegates to the platform's RTPScheduler. Platforms
     * that already expose scheduling (Bukkit, Folia, Paper, Fabric) need not
     * override.
     */
    default RTPScheduledHandle schedulePeriodic(String taskLabel, long initialDelayMs,
                                                long periodMs, Runnable task) {
        // default delegates to RTP.scheduler (rtp-api already references it
        // via the existing RTPScheduler abstraction).
        return DefaultSchedulingBridge.schedulePeriodic(this, taskLabel,
                initialDelayMs, periodMs, task);
    }

    /**
     * Monotonic millisecond clock. Defaulted to System.currentTimeMillis().
     * Overridable for deterministic tests (an existing rtp-api convention -
     * MetricsBinding already uses Clock injection).
     */
    default long currentTimeMillis() {
        return System.currentTimeMillis();
    }

    /**
     * Stable identifier for this physical server within the network. Sourced
     * from network.yml network.serverId. Returns null when network mode is
     * disabled.
     */
    default String networkServerId() {
        return null;
    }

    /**
     * Log routed through the platform's logger. Existing rtp-api convention
     * already exposes log(Level, String, Throwable); this primitive is named
     * for clarity from inside transport code.
     */
    default void networkLog(java.util.logging.Level lvl, String msg, Throwable t) {
        log(lvl, msg, t); // default to existing log() method
    }
}

    RTPScheduledHandle is a tiny new rtp-api interface:

    public interface RTPScheduledHandle extends AutoCloseable {
    boolean isCancelled();
    @Override void close(); // idempotent cancel
}

    That is the full additive surface on RTPServerAccessor. No proxy-shaped types leak into rtp-api. No new static slots.

    4. NetworkTransport after the refactor¶

    The interface stays the same (existing public methods retained). What changes is the abstract base class that bindings extend.

    package io.github.dailystruggle.rtp.proxy.common.spi;

public abstract class AbstractNetworkTransport implements NetworkTransport {

    protected final RTPServerAccessor host;
    protected final List<Consumer<BackendHeartbeat>> backendSinks =
            new CopyOnWriteArrayList<>();
    protected final List<Consumer<ProxyHeartbeat>> proxySinks =
            new CopyOnWriteArrayList<>();
    protected volatile RTPScheduledHandle pollHandle;

    protected AbstractNetworkTransport(RTPServerAccessor host) { this.host = host; }

    // Shared poll-loop scaffolding. Bindings override doPollOnce() with the
    // transport-specific read (JDBC SELECT for SQL; ConcurrentHashMap copy for
    // in-memory; Redis SCAN for future Redis).
    protected final void startPolling(String label, long intervalMs) {
        pollHandle = host.schedulePeriodic(label, intervalMs, intervalMs, () -> {
            try { doPollOnce(); }
            catch (Throwable t) {
                host.networkLog(Level.WARNING, label + " poll failed: " + t, t);
            }
        });
    }

    protected abstract void doPollOnce();

    // Shared subscriber-fanout. Bindings just call fanOutBackend(row) once
    // they have determined a heartbeat is new / changed.
    protected final void fanOutBackend(BackendHeartbeat row) {
        for (Consumer<BackendHeartbeat> s : backendSinks) {
            try { s.accept(row); }
            catch (Throwable t) { host.networkLog(Level.WARNING, "backend sink threw", t); }
        }
    }
    protected final void fanOutProxy(ProxyHeartbeat row) { /* mirror */ }

    @Override
    public final Subscription subscribeBackendHeartbeats(Consumer<BackendHeartbeat> sink) {
        backendSinks.add(sink);
        return () -> backendSinks.remove(sink);
    }

    @Override
    public void close() {
        if (pollHandle != null) pollHandle.close();
        backendSinks.clear();
        proxySinks.clear();
    }
}

    After the refactor:

    • InMemoryNetworkStateBinding extends AbstractNetworkTransport - drops its own subscriber list, its own clock reads, its own scheduling. Shrinks from ~150 LOC to ~80.
    • SqlNetworkStateBinding extends AbstractNetworkTransport - drops its own poll loop, its own subscriber list, its own clock reads. Shrinks from ~475 LOC to ~320.
    • Future RedisNetworkStateBinding plugs straight into the same scaffolding; ~250 LOC instead of starting from scratch.
    • No per-platform subclass. Each transport type is one class, period.

    AbstractNetworkTransport lives in rtp-proxy-common. It depends on RTPServerAccessor from rtp-api, which is already the case (rtp-proxy-common -> rtp-api).

    5. How the test job reaches the live transport¶

    The refactor does not, by itself, solve "how does NetworkSimulationTestJob in rtp-core find the live transport on this JVM?". Two cheap options remain; neither is RTP.networkTransport and neither is RTPServerAccessor.networkTransport().

    Both options are platform-agnostic. Pick one:

    Option P (recommended). Bridge through the existing D3 slot.¶

    AbstractSQLDatabaseAccessor.setNetworkStateBinding(...) is already called by NetworkModeBootstrap.boot() (Phase 2e-SQL slice, line 104). The slot today holds a SqlBindingAdapter whose transport() accessor is package-private.

    Action:

    • Promote the NetworkStateBinding interface (rtp-core) to expose a default NetworkTransport transport() { return null; } method.
    • SqlBindingAdapter.transport() becomes the override.
    • InMemoryNetworkStateBinding does NOT implement NetworkStateBinding - but the in-memory case in NetworkModeBootstrap wraps it in a tiny InMemoryBindingAdapter implements NetworkStateBinding the same way SQL does.
    • Test job: RTP.serverAccessor.databaseAccessor() instanceof AbstractSQLDatabaseAccessor sql -> sql.getNetworkStateBinding() -> transport(). Any null link = skip with NOT-CONFIGURED.

    Pro: no new types in rtp-api. Pro: Fabric route is the same code path - NetworkStateBinding is already in rtp-core. Con: leaks NetworkTransport type onto NetworkStateBinding (was opaque marker). But: rtp-core already has an api dep on rtp-proxy-common since the Phase 2e-SQL turn, so the import is mechanical, not architectural.

    Option Q. Visitor on RTPServerAccessor.¶

    RTPServerAccessor gains default <T> T queryNetworkPrimitive(Class<T> kind) { return null; }. Platform ServerAccessor impls override to return the live transport when asked for NetworkTransport.class. Generic, future-proof for other "what platform has X" queries, but more ceremony for the single use site we have today.

    Recommendation: P, with Q kept as a fallback if it turns out Fabric needs a different lookup path.

    6. NetworkSimulationTestJob (the actual test surface)¶

    6.1 Placement¶

    rtp-core/src/main/java/io/github/dailystruggle/rtp/common/commands/test/NetworkSimulationTestJob.java.

    Registered in the TestCmd base class (not BukkitTestCmd), so the subcommand rtp test network is available on every platform that ships rtp test.

    6.2 Command shape¶

    /rtp test network            (default: simulate 3 peers, 5s observation window)
/rtp test network <N>        (override peer count, clamped 1..16)
/rtp test network <N> <ms>   (override observation-window ms, clamped 250..30_000)

    Permission: rtp.test (mirrors siblings).

    6.3 Lifecycle¶

    1. Resolve transport. Reach the live transport via Option P (§5). If null, emit network: NOT-CONFIGURED and return PASS-with-skip (consistent with REQ-RTP-NET-002 - disabled mode means the test is not applicable, not failed).
    2. Register with ActiveTestJobs. Mirrors EconomyIsolationTestJob pattern so rtp test full blocks on us if invoked from the umbrella.
    3. Deterministic synthetic peers. Seed = callerId.getMostSignificantBits() ^ jobId.hashCode(). Generate N BackendHeartbeats with synthesised UUIDs UUID.nameUUIDFromBytes(("rtp-sim-" + seed + "-" + i).getBytes(UTF_8)), pluginState=READY, randomised TPS (16..20), MSPT (10..40), load (0..0.8).
    4. Subscribe to the transport. Capture a thread-safe set of UUIDs the subscriber observes (used in step 7).
    5. Publish. Call transport.publishBackendHeartbeat(row) for each synthetic peer. Await all futures with a 2s aggregate timeout (PROBE_TIMEOUT_MS, mirroring EconomyIsolationTestJob).
    6. Wait one observation window. Default 5s. Lets the poll loop on SQL bindings pick up the rows; in-memory bindings fan out synchronously on publish so this window is a forgiving cushion, not a requirement.
    7. Assert.
    8. Local transport.readSnapshot() contains all N synthetic UUIDs.
    9. The subscriber observed exactly N fan-out events for those UUIDs (or >= N if the binding republishes on poll, with the SQL-side caveat called out below).
    10. WeightedAverageBackendSelector.select(snapshot, deterministicSeed) produces the same winner across three repeated calls (REQ-RTP-NET-013).
    11. Cleanup. Always - normal exit, exception, or command-source disconnect. Publish a "leave" heartbeat for each synthetic UUID (pluginState=STOPPING) AND immediately call transport.publishBackendHeartbeat(row) with the row's lastHeartbeatAt set to 0 / a far-past value so the binding's TTL reaper drops it within the next poll cycle. For SQL specifically, also issue a direct DELETE on the synthetic UUIDs through the same RTPServerAccessor primitive (added in §3 if not already present, but ideally NOT - cleanup should ride the existing transport API; see open question Q1).
    12. Audit. Emit one network: PASS / FAIL <reason> / NOT-CONFIGURED line via SendMessage, so rtp test full's FullAudit captures the row.

    6.4 What it does NOT do¶

    • Does not test HMAC reject paths (Phase 4 / ADR-010 territory).
    • Does not test multi-JVM agreement (requires real devstack).
    • Does not test churn or partition (Shape B territory).
    • Does not test reservation-token claim races (single-JVM only - both claimants are the same transport instance, so the race is trivial).

    These are deliberately deferred per the original Shape A scope.

    6.5 REQ-RTP-NET-002 parity¶

    Disabled mode must be byte-identical no-op. Test job preconditions check RTP.serverAccessor.networkServerId() == null (§3 primitive); if null, do not touch the transport at all, do not subscribe, do not allocate a ScheduledExecutor. Emit NOT-CONFIGURED and return.

    7. Implementing turn worklist (after this proposal is approved)¶

    1. rtp-api: add RTPScheduledHandle, the four default methods on RTPServerAccessor (§3). DefaultSchedulingBridge helper in rtp-api or rtp-core depending on dep direction.
    2. rtp-proxy-common: introduce AbstractNetworkTransport; refactor InMemoryNetworkStateBinding and SqlNetworkStateBinding to extend it; delete duplicated scaffolding. Update tests (existing 6+3 should still pass without semantic changes; if they don't, that is a bug in the refactor, not the tests).
    3. rtp-core: amend NetworkStateBinding to expose default NetworkTransport transport() { return null; }. Add InMemoryBindingAdapter for symmetry with SqlBindingAdapter.
    4. rtp-plugin: NetworkModeBootstrap populates the D3 slot for both SQL and in-memory paths.
    5. Each platform ServerAccessor (Bukkit, Folia, Paper, Fabric): override networkServerId() to return the value pulled from NetworkModeBootstrap (or null on Fabric until network bootstrap lands there). No other overrides required; defaults cover the rest.
    6. rtp-core: write NetworkSimulationTestJob per §6. Register in TestCmd base.
    7. TRACEABILITY.md: row for the new REQ (proposed: REQ-RTP-NET-015 - Simulated Peer Diagnostic).
    8. MULTI_SERVER_PLAN.md: tick H3 ("rtp test full network aggregator") partially (single-JVM half landed; cross-process half deferred to Phase 2f). Add Shape A landing callout.
    9. LESSONS_LEARNED.md: row explaining what Shape A does NOT cover so operators don't get false confidence.
    10. Tests: NetworkSimulationTestJob unit test using InMemoryNetworkStateBinding; refactor regression tests for the two existing bindings.
    11. Full gradlew build.

    Estimated LOC: ~500 LOC code (mostly refactor; net new is ~200 LOC for the test job + ~80 LOC for the rtp-api primitives + ~50 LOC for the D3-slot plumbing). ~250 LOC of test code.

    8. Open questions¶

    Q1. Synthetic peer cleanup primitive.¶

    Step 6.3.8 wants the test to be able to delete a row immediately, not wait for TTL. Options:

    • (a) Extend NetworkTransport with removeBackendHeartbeat(UUID). Cleanest. Every binding can implement it trivially.
    • (b) Publish a STOPPING-state heartbeat and let the binding's reaper drop it on the next poll. Lower API surface but means the test sleeps one poll interval during cleanup.

    Default recommendation: (a). Symmetric with existing publish/snapshot surface, cleaner test exit, useful beyond this test job (admin tooling for evicting ghost backends).

    Q2. Should the test job run on the in-memory binding at all?¶

    If transport.type: in-memory on a single JVM, the test is essentially a self-check (no real cross-process state to assert against). Still useful as a smoke test (proves the transport plumbing, subscribe/fan-out, selector determinism) but easy to misread as a multi-server-readiness check.

    Default recommendation: run unconditionally; emit a NETWORK: PASS (in-memory; single-JVM only) suffix in the audit row to make the limitation explicit.

    Q3. Scheduling-bridge dep direction.¶

    DefaultSchedulingBridge (§3) needs to call RTP.scheduler. RTP is in rtp-core. RTPServerAccessor is in rtp-api. If the bridge lives in rtp-api, it cannot reach RTP.scheduler. If it lives in rtp-core, then the default method on RTPServerAccessor calls into rtp-core - which rtp-api also cannot do.

    Resolution: the default method delegates to an existing rtp-api primitive (RTPScheduler is already in rtp-api per the existing scheduling abstraction; RTPServerAccessor already has access to one via the existing scheduler() or equivalent). Verify during implementation; if not, the cleaner fix is for each platform's concrete ServerAccessor to override schedulePeriodic directly.

    Q4. Is RTPServerAccessor the right home for networkServerId()?¶

    It is tied to network mode, not the server-platform abstraction. An argument exists for putting it on a separate RTPNetworkAccessor interface in rtp-api. Counter-argument: it is fundamentally "what is this server's identity in the network" which is server-shaped data, and putting it on RTPServerAccessor keeps the platform-abstraction surface unified.

    Default recommendation: leave it on RTPServerAccessor with a clear Javadoc that it returns null when network mode is disabled. Re-home later if a richer RTPNetworkAccessor surface emerges.

    Q5. Refactor scope: now vs. incrementally.¶

    The proposal lands the refactor and the test job in the same turn (~500 LOC code change + tests). An alternative is to land Shape A first using Option P (D3 slot + transport accessor) against today's binding shape, then do the AbstractNetworkTransport refactor as a follow-up turn.

    Default recommendation: per user direction ("worth doing eventually is best done immediately here"), land both in one turn.

    9. What this proposal explicitly does NOT change¶

    • network.yml schema (ADR-002 stable).
    • NetworkConfig SPI in rtp-proxy-common.
    • ReservationToken SPI (ADR-005 already Accepted).
    • BackendSelector / WeightedAverageBackendSelector (the test uses them read-only).
    • The Phase 2e-SQL slice's external behaviour - bindings continue to produce the same SQL DDL, same UPSERT semantics, same atomic-claim contract. Only the internal scaffolding moves.
    • ADR statuses. rtp-proxy-ADR-005, -010, -011 all remain as-is.
    • Velocity-side wiring. rtp-proxy-velocity does not need changes; the Velocity adapter already constructs its transport via NetworkBindings.open().

    10. Decision needed¶

    • Approve §3 primitives (schedulePeriodic, currentTimeMillis, networkServerId, networkLog) on RTPServerAccessor. Override or add others.
    • Approve §4 AbstractNetworkTransport shape. Or push back if you'd rather keep each binding standalone.
    • Approve §5 Option P (D3-slot bridge with promoted transport() accessor on NetworkStateBinding). Or pick Q.
    • Approve §6 NetworkSimulationTestJob design.
    • Answer Q1-Q5 in §8 (defaults documented; saying "all defaults" is fine).

    Once approved, the implementing turn is one D-005-compliant pass covering §7's 11 steps, ending with a full multi-module build.
