    PROPOSAL: proxy-direct = a simple, redis-equivalent data-management transport¶

    Status: DRAFT (design-first; awaiting user approval before implementation) Supersedes (on acceptance): the bespoke teleport leg of rtp-proxy-ADR-018 (OP_ENROL / OP_REDEEM_QUERY + ProxyDirectRedeemListener). Keeps: rtp-proxy-ADR-017 (the player-independent backend->proxy TCP socket).

    1. Goal (the one-sentence contract)¶

    proxy-direct shall be exactly what redis and sql already are -- a NetworkTransport + NetworkRequestQueue binding pair backed by a single shared store -- except the shared store is the proxy's own in-memory maps, reached over the existing proxy-direct TCP socket instead of a Redis/JDBC server.

    Litmus test for "simple option other than redis for data management": every cross-server behaviour (region discovery, enrolment, dispatch, reservation, arrival redeem) must run through the same SPI calls and the same proxy-side code that the Redis tier uses. The only thing that changes between transport.type: redis and transport.type: proxy-direct is where the bytes land. No teleport-specific opcodes, no parallel arrival listener.

    2. The mental model (who is the "redis server")¶

    Role Redis tier proxy-direct tier
    The shared store external Redis the proxy JVM's InMemoryNetworkStateBinding + InMemoryNetworkRequestQueue (already constructed today, RtpVelocityPlugin lines 197/213/278)
    Backend transport RedisNetworkStateBinding (client) ProxyDirectNetworkBinding (RPC client)
    Backend queue RedisNetworkRequestQueue (client) ProxyDirectNetworkRequestQueue (RPC client, new)
    The wire RESP over TCP to Redis length-prefixed HMAC frames over TCP to the proxy listener (already exists)

    The proxy is the always-on process, so it plays the part Redis plays: it owns the data; backends are stateless clients that read/write it. This is precisely the user's "the proxy server takes the role of the redis server."

    3. What already works and is REUSED unchanged¶

    On the proxy, in proxy-direct mode, these are already constructed and running (verified in RtpVelocityPlugin.onProxyInitialize):

    • transport = InMemoryNetworkStateBinding (the store for heartbeats + reservations).
    • requestQueue = in-memory NetworkRequestQueue (the enrolment FIFO).
    • DefaultRtpDispatcher (selector + transport.claim + sender.createConnectionRequest).
    • TransportRequestTriggerSource (drains the queue, feeds the dispatcher).
    • ReservationTokenReaper, the ServerPreConnectEvent redeem listener, the waitlist drainer.

    None of this changes. Today it operates on an empty store because backends write to their own separate in-memory instances. The whole fix is: point the backends' SPI calls at the proxy's instances.

    4. The change (minimal, SPI-shaped)¶

    4.1 Wire (ProxyDirectWire) -- generic RPC, not teleport verbs¶

    Replace OP_PUSH / OP_ENROL / OP_REDEEM_QUERY with one opcode per SPI method actually invoked from a backend (the only RPC direction; the proxy never dials a backend):

    OP_HEARTBEAT_AND_SNAPSHOT  // publishBackendHeartbeat(row) -> readSnapshot rows   (= today's PUSH)
OP_FLUSH_PENDING           // NetworkRequestQueue.flushPending(batch) -> EnrolOutcome
OP_POLL_STATUS             // NetworkRequestQueue.pollStatus(ids)     -> List<QueueStatus>
OP_CANCEL                  // NetworkRequestQueue.cancel(id, reason)  -> ack
OP_FIND_RESERVATION        // NetworkTransport.findReservation(id)    -> Optional<ReservationToken>
OP_REDEEM                  // NetworkTransport.redeem(tok,id,server)  -> RedeemOutcome
OP_LIST_ACTIVE_FOR_SERVER  // NetworkTransport.listActiveForServer(s) -> List<ReservationToken>

    Each frame: byte opcode, one signed request payload (delimited fields), one signed response payload (or count+rows for list returns). HMAC + framing helpers are reused verbatim. Request fields are simple strings (UUIDs, server ids, region keys, enum names); ReservationToken serialises its 6 fields (tokenId, serverId, playerId, expiresEpochMs, state, regionKey).

    Methods that are proxy-local only are never RPC'd: claim, dequeueReady, transition, release, reapExpired, publishProxyHeartbeat, subscribeBackendHeartbeats. They run on the proxy against its own store, as today.

    4.2 Backend client (rtp-core)¶

    • ProxyDirectNetworkBinding (existing) becomes a full RPC NetworkTransport: publishBackendHeartbeat, readSnapshot (as today), plus findReservation, redeem, listActiveForServer via RPC. claim throws UnsupportedOperationException (a backend never claims; the proxy does). release/publishProxyHeartbeat stay no-ops (proxy-side concerns).
    • ProxyDirectNetworkRequestQueue (new, rtp-core) implements NetworkRequestQueue: enrol/flushPending/pollStatus/cancel via RPC; dequeueReady returns empty and transition returns empty (backends never drain -- those are proxy-local).

    4.3 NetworkModeBootstrap (rtp-core)¶

    • openRequestQueue("proxy-direct") returns the new remote queue instead of null. The existing flush-sink wiring (NetworkEnrolmentBuffer -> requestQueue.flushPending) then lights up with no special-casing -- the same code path the SQL/Redis tiers use.
    • Delete the proxyDirectRedeemListener field + its registration. Arrival redeem returns to the standard JoinTriggerSource (it already calls transport.findReservation + transport.redeem, which now RPC to the proxy).

    4.4 Proxy listener (rtp-proxy-velocity)¶

    • ProxyDirectListener gains an RPC dispatch switch that calls the already- built transport and requestQueue instances (passed in from RtpVelocityPlugin, replacing the current onPush/snapshotRows/onEnrol/ onRedeemQuery lambdas). OP_HEARTBEAT_AND_SNAPSHOT keeps feeding the availability cache for tab-completion.
    • Delete onProxyDirectEnrol / onProxyDirectRedeemQuery / the proxyDirectPending TTL map. The dispatcher's createConnectionRequest (driven by the trigger source) now performs the move, and claim records the reservation the arriving backend redeems.

    5. End-to-end flow after the change (identical to Redis, different bytes)¶

    1. Backend boot: publishBackendHeartbeat (RPC) -> proxy store has its regions -> lobby readSnapshot (RPC) -> /rtp region= tab-completion populated. (Zero players; unchanged from today.)
    2. Lobby /rtp region=backend-a:default: router enrols -> NetworkEnrolmentBuffer flush -> flushPending (RPC) -> proxy's in-memory queue.
    3. Proxy TransportRequestTriggerSource dequeues -> dispatcher selects backend -> transport.claim writes a reservation into the proxy store -> sender.createConnectionRequest moves the player. (All existing proxy code.)
    4. Player lands on backend-a: standard JoinTriggerSource -> findReservation (RPC) -> redeem (RPC) -> local /rtp region=default. (All existing code.)

    6. Reservations: kept this pass (explicit)¶

    Per the user's note, "no per-player reservations" is a future cleanup about an already-implemented concept, not a constraint on this refactor. This proposal keeps reservation tokens so the arrival path reuses JoinTriggerSource verbatim. A later, separate change may slim the proxy-direct store to a region-only pending map if desired; it is out of scope here.

    7. Why this is "simple" (and not more than needed)¶

    • Net new types: one (ProxyDirectNetworkRequestQueue). Everything else is edits to existing files.
    • Net deleted surface: the three bespoke teleport opcodes, ProxyDirectRedeemListener, and the proxy-side pending-map + enrol/redeem lambdas.
    • Zero new concepts on the proxy: the dispatcher, trigger source, reaper, and preconnect redeem are untouched.
    • transport.type switches a backend between redis, sql, and proxy-direct with no behavioural branches anywhere except the binding factory -- the definition of a drop-in data-management option.

    8. Risks / decisions for sign-off¶

    1. Blocking RPC on backend threads. Each RPC opens a short-lived socket. publishBackendHeartbeat/readSnapshot already do this on the scheduler tick. findReservation/redeem run from JoinTriggerSource; they must be dispatched on RTP.scheduler's async tier (as the retired redeem listener already did) so no join/tick thread blocks. flushPending/pollStatus run from the existing buffer/status-cache timers (already async).
    2. One socket per RPC vs. pooling. Simplest correct choice is one connect-per-call (matches today's heartbeat exchange). Acceptable for lite scale; a keep-alive pool is a later optimisation, not needed for correctness.
    3. Multi-proxy. A backend dials every configured proxy. For reservations the first definite answer wins (as the snapshot read already does). Cross-proxy ownership is a durable-tier concern; proxy-direct remains single-proxy-simple and is documented as such.
    4. ADR. On approval, supersede the teleport portion of rtp-proxy-ADR-018 with a new rtp-proxy-ADR (or a revision) recording "proxy-direct = remote in-memory store across the full SPI."

    9. Out of scope¶

    • The region-publish limiter (deferred earlier by the user).
    • Reservation removal (section 6).
    • Keep-alive/pooled sockets, Postgres LISTEN/NOTIFY, BungeeCord.
