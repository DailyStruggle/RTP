    PROPOSAL: Phase 2e (SQL slice) - SqlNetworkStateBinding + Backend-Side Network Wiring¶

    Status: Proposed (docs-only, D-005 gating turn) Author: Junie session 2026-05-18 Scope: the minimum cut to make a real cross-process runtime test possible: 1 Velocity proxy + 2 Paper backends + 1 shared SQL DB, all of them seeing each other's heartbeats in a shared table. Supersedes nothing. Folds the SQL slice of rtp-proxy-ADR-011-sql-network-state-binding (Proposed) into a concrete implementation plan and pairs it with the missing backend-side publisher.

    1. Goal¶

    After this proposal lands as code, the following devstack smoke test passes:

    1. Start 1x Velocity 3.3 + 2x Paper 1.21 + 1x MySQL 8 (or Postgres 16).
    2. All three JVMs read the same network.yml template with enabled: true, transport.type: sql, identical secretEnv (unused for SQL - see Q1), distinct proxyId / serverId.
    3. Within 2 * heartbeat.intervalMs of the last JVM booting, SELECT * FROM rtp_network_proxies returns 1 row and SELECT * FROM rtp_network_backends returns 2 rows.
    4. Killing either backend causes its row's last_seen_ms to stop advancing; after 3 * heartbeat.intervalMs the proxy's NetworkSnapshot no longer lists it as fresh.

    That is the only acceptance criterion for this phase. No /rtp cross-server teleport, no ServerPreConnectEvent, no Brigadier /network status - those are Phase 2c / 2d / 2g.

    2. Non-goals (deferred)¶

    • Reservation token claim contention testing (claim / release are implemented but not exercised end-to-end until Phase 2c lands ServerPreConnectEvent).
    • HMAC / kill-switch wire enforcement (ADR-010): the SQL binding leans on DB connection auth + TLS; HMAC fields stay zeroed. Documented as N/A per PROPOSAL-sql-binding-first.md rev 2.
    • Redis binding (Phase 2e-Redis): peer to this, separate D-005 turn.
    • network.yml ships shaped but without Redis stanzas wired - those are skeleton-only.
    • Metrics axis. No MetricsBinding taps yet.

    3. Architectural shape¶

    3.1 Module placement¶

    rtp-proxy-common/
  src/main/java/.../proxy/common/transport/sql/
    SqlNetworkStateBinding.java          (NEW; implements NetworkTransport)
    SqlNetworkStateBindingFactory.java   (NEW; opens from JDBC URL + creds)
    SqlNetworkStateSchema.java           (NEW; DDL bootstrap)
    SqlHeartbeatPoller.java              (NEW; periodic SELECT + fan-out)
  src/test/java/.../proxy/common/transport/sql/
    SqlNetworkStateBindingH2Test.java    (NEW; H2 in-memory, two-instance fan-out)

    rtp-proxy-common already depends on rtp-api (no JDBC there) - we add org.xerial:sqlite-jdbc and com.h2database:h2 as testRuntimeOnly, real production JDBC drivers (MySQL / Postgres) stay the deployer's responsibility (matching AbstractSQLDatabaseAccessor's philosophy in rtp-core).

    Open question Q2: Do we share rtp-core's HikariCP-backed pool from AbstractSQLDatabaseAccessor, or does the SQL binding own its own small pool? See §7.

    3.2 Backend-side wiring (the other half)¶

    rtp-core/
  src/main/java/.../common/network/
    BackendStatePublisher.java           (NEW; mirrors ProxyStatePublisher)
    BackendStateSampler.java             (NEW; interface: snapshot() -> BackendHeartbeat row data)
  src/test/java/.../common/network/
    BackendStatePublisherTest.java       (NEW; deterministic cadence test)

rtp-plugin/src/main/resources/
  network.yml                            (NEW template; shipped, defaults to enabled:false)

platforms/rtp-bukkit/rtp-bukkit-common/
  src/main/java/.../bukkit/common/network/
    BukkitBackendStateSampler.java       (NEW; reads TPS/MSPT/playerCount from Bukkit)

rtp-plugin/
  src/main/java/.../bukkit/RTPBukkitPlugin.java
    (EDIT) onEnable: if network.yml -> enabled:true, open binding,
                     setNetworkStateBinding on DB accessor, start BackendStatePublisher
    (EDIT) onDisable: stop publisher in reverse order, close binding

    rtp-core's BackendStatePublisher is platform-agnostic - it takes a BackendStateSampler SPI that each adapter implements. Mirrors how RTP.serverAccessor works.

    4. SqlNetworkStateBinding shape¶

    Public surface is exactly NetworkTransport. No new SPI. Internal shape:

    public final class SqlNetworkStateBinding implements NetworkTransport {
    private final DataSource ds;                     // Hikari, see Q2
    private final Supplier<Instant> clock;
    private final SqlHeartbeatPoller poller;         // owns 1 daemon thread
    private final CopyOnWriteArrayList<Sub> subs;
    private final AtomicBoolean closed;
    private final String dialect;                    // h2 | sqlite | mysql | postgresql

    @Override public CompletableFuture<NetworkSnapshot> readSnapshot();
    @Override public CompletableFuture<ReservationToken> claim(...);
    @Override public CompletableFuture<Void> release(...);
    @Override public CompletableFuture<Void> publishProxyHeartbeat(...);
    @Override public Subscription subscribeBackendHeartbeats(...);
    @Override public void close();
}

    4.1 SPI -> SQL mapping¶

    NetworkTransport method SQL action
    publishProxyHeartbeat(row) INSERT INTO rtp_network_proxies ... ON CONFLICT(proxy_id) DO UPDATE SET ... (UPSERT)
    readSnapshot() SELECT * FROM rtp_network_backends WHERE last_seen_ms > ? - ? (now - staleness budget); returns NetworkSnapshot(nowMs, backendsMap)
    claim(serverId, playerId, ttl) one of two strategies, see §4.3
    release(tokenId, reason) UPDATE rtp_network_tokens SET state = ?, released_at_ms = ? WHERE token_id = ? (idempotent on missing row)
    subscribeBackendHeartbeats(sink) sink stored in subs; SqlHeartbeatPoller fires sink.accept(row) every poll cycle for newly observed or refreshed rows

    Backend-side publish (the missing direction): SqlHeartbeatPoller.publishBackendHeartbeat(row) does the same UPSERT against rtp_network_backends. The SPI does not currently expose this method; we add it as default on NetworkTransport (additive, in-memory binding implements it identically via publishBackendHeartbeat which already exists as a test affordance). This is the one SPI tweak.

    4.2 DDL bootstrap (SqlNetworkStateSchema)¶

    Idempotent CREATE TABLE IF NOT EXISTS on binding.open(). Per-dialect tweaks via switch on dialect. Sketch:

    -- rtp_network_proxies
CREATE TABLE IF NOT EXISTS rtp_network_proxies (
    proxy_id        VARCHAR(64)  NOT NULL PRIMARY KEY,
    last_seen_ms    BIGINT       NOT NULL,
    player_count    INT          NOT NULL,
    kill_switch     BOOLEAN      NOT NULL DEFAULT FALSE,
    schema_version  INT          NOT NULL,
    updated_at_ms   BIGINT       NOT NULL
);

-- rtp_network_backends
CREATE TABLE IF NOT EXISTS rtp_network_backends (
    server_id       VARCHAR(64)  NOT NULL PRIMARY KEY,
    last_seen_ms    BIGINT       NOT NULL,
    tps             DOUBLE       NOT NULL,
    mspt            DOUBLE       NOT NULL,
    player_count    INT          NOT NULL,
    queue_depth     INT          NOT NULL,
    kill_switch     BOOLEAN      NOT NULL DEFAULT FALSE,
    schema_version  INT          NOT NULL,
    updated_at_ms   BIGINT       NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_backends_last_seen ON rtp_network_backends(last_seen_ms);

-- rtp_network_tokens
CREATE TABLE IF NOT EXISTS rtp_network_tokens (
    token_id        VARCHAR(64)  NOT NULL PRIMARY KEY,
    server_id       VARCHAR(64)  NOT NULL,
    player_id       VARCHAR(36)  NOT NULL,
    expires_at_ms   BIGINT       NOT NULL,
    state           VARCHAR(16)  NOT NULL,    -- PENDING | CLAIMED | CONSUMED | RELEASED | EXPIRED
    created_at_ms   BIGINT       NOT NULL,
    released_at_ms  BIGINT
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_tokens_active_player
    ON rtp_network_tokens(player_id) WHERE state IN ('PENDING','CLAIMED');
-- (the partial index is Postgres / SQLite; MySQL needs a trigger or active-only table)

    schema_version is REQ-RTP-NET-010 propagation; mismatched versions are logged and ignored on read.

    4.3 Atomic claim (two strategies, dialect-gated)¶

    • Postgres / MySQL 8+ / H2: INSERT INTO rtp_network_tokens (...) VALUES (...). The partial unique index on player_id enforces per-player idempotency at the DB level. Catch SQLIntegrityConstraintViolationException -> throw IllegalStateException("Reservation race") matching in-memory semantics.
    • SQLite / older MySQL: SELECT ... FOR UPDATE then INSERT inside a single transaction. Slightly slower; acceptable since SQLite is dev-only.

    The PENDING -> CLAIMED transition is collapsed into a single INSERT ... VALUES (..., 'CLAIMED', ...) in the SQL binding (the in-memory two-step exists for race-test scaffolding; SQL gets atomicity from the DB).

    4.4 SqlHeartbeatPoller¶

    Single daemon thread, name rtp-proxy-sql-poller. Loop:

    loop:
    sleep(network.transport.sql.pollIntervalMs)    // default 1000
    if closed: break
    try:
        nowMs = clock()
        staleAfterMs = network.heartbeat.staleAfterMs   // default 5000
        rows = SELECT * FROM rtp_network_backends WHERE last_seen_ms > nowMs - staleAfterMs
        for each row not in lastSeenCache or with newer updated_at_ms:
            for each sub: sub.sink.accept(row)
        lastSeenCache = rows.indexBy(serverId)
    catch SQLException: log WARNING, continue (transient DB blip is not fatal)

    Polling overhead at N backends: O(1) query/sec/JVM. At 1Hz poll on a LAN MySQL: ~5-30ms per poll, negligible. Open question Q3: does this scale past N=32 without LISTEN/NOTIFY?

    5. Backend-side publisher¶

    5.1 BackendStatePublisher (in rtp-core)¶

    Mirror of ProxyStatePublisher:

    public final class BackendStatePublisher {
    private final NetworkTransport transport;
    private final BackendStateSampler sampler;
    private final ScheduledExecutorService scheduler;   // 1 daemon thread
    private final long intervalMs;
    private final AtomicBoolean running = new AtomicBoolean();

    public void start();    // idempotent
    public void stop();     // idempotent, joins with 2s deadline (ADR-006 parity)
}

    Cadence: network.heartbeat.intervalMs (default 1000). On each tick:

    row = sampler.sample(nowMs)
transport.publishBackendHeartbeat(row)    // new default method on NetworkTransport

    5.2 BackendStateSampler (SPI in rtp-core)¶

    public interface BackendStateSampler {
    BackendHeartbeat sample(long nowMs);
}

    Adapter implementations (only one in this phase):

    • BukkitBackendStateSampler (in rtp-bukkit-common): pulls TPS / MSPT from existing metrics taps, Bukkit.getOnlinePlayers().size(), queue depth from RegionQueueManager.keptLocations.size() (or equivalent - see Q4).

    Folia / Paper inherit Bukkit's. Fabric: deferred.

    5.3 Boot wiring in RTPBukkitPlugin¶

    Pseudocode (real PR will respect existing init order):

    @Override
public void onEnable() {
    super.onEnable();
    // ... existing setup ...

    File networkYml = new File(getDataFolder(), "network.yml");
    if (!networkYml.exists()) saveResource("network.yml", false);
    NetworkConfig netCfg = NetworkConfig.fromMap(toNestedMap(RtpYamlConfig.load(networkYml)));
    if (!netCfg.enabled()) {
        // REQ-RTP-NET-002 byte-identical no-op: no binding, no publisher, no thread.
        return;
    }
    NetworkTransport binding = openBindingForType(netCfg);  // sql | inMemory | redis-later
    ((AbstractSQLDatabaseAccessor) RTP.databaseAccessor).setNetworkStateBinding(binding);
    BukkitBackendStateSampler sampler = new BukkitBackendStateSampler(this, netCfg.serverId());
    BackendStatePublisher publisher = new BackendStatePublisher(binding, sampler,
            netCfg.heartbeatIntervalMs());
    publisher.start();
    // store handles for onDisable
}

    network.yml template (new resource):

    # Network mode. Disabled by default; flip to true on every backend AND every proxy.
network:
  enabled: false
  serverId: "backend-1"   # MUST be unique per backend
  transport:
    type: "sql"           # sql | inMemory | redis (Redis: Phase 2e-Redis)
    sql:
      # Defaults to sharing the main RTP database (see Q2).
      pollIntervalMs: 1000
  heartbeat:
    intervalMs: 1000
    staleAfterMs: 5000
  schemaVersion: 1

    (On the proxy side, the existing template adds proxyId and secretEnv; we keep them divergent for now - proxies don't need serverId, backends don't need proxyId.)

    6. Test plan¶

    6.1 Unit (this turn's [CODE] follow-up)¶

    1. SqlNetworkStateBindingH2Test:
    2. Boots H2 in-memory.
    3. Opens two SqlNetworkStateBinding instances against the same JDBC URL.
    4. Instance A: publishProxyHeartbeat(...); instance B: readSnapshot() -> sees the row (well, proxy heartbeat doesn't appear in NetworkSnapshot which only carries backends - tested separately via dumpProxies()-equivalent SELECT).
    5. Instance A: publishBackendHeartbeat(...); instance B's subscriber fires within 2 * pollIntervalMs.
    6. Instance A: claim(...); instance B's claim(...) for same player throws IllegalStateException.

    7. DDL is idempotent across open() calls.

    8. BackendStatePublisherTest:

    9. Deterministic clock; assert sampler called every intervalMs (+/- jitter budget).
    10. stop() joins within deadline.
    11. stop() is idempotent.

    The Goal block at the top of this doc. Runs against a real docker-compose; not automated this turn.

    6.3 No-op parity (regression guard)¶

    Extend ReqRtpNet002NetworkDisabledNoOpTest (in rtp-core) with one new assertion: when network.enabled:false, RTPBukkitPlugin.onEnable does not call setNetworkStateBinding(...) on the DB accessor. Currently it can't call it because the field is null; we lock that in.

    7. Open questions¶

    Q1. secretEnv semantics for the SQL binding. ADR-010 requires HMAC over wire envelopes; SQL has no envelope, just rows. Recommendation: secretEnv is read but unused when transport.type: sql (logged as INFO at boot: "transport=sql; HMAC verification N/A, relying on DB transport auth"). Same env var is required by the Redis binding so a network can switch without re-configuring backends. Confirm.

    Q2. HikariCP pool sharing. Two options: - A. SqlNetworkStateBinding owns its own small pool (2-4 conns), independent of AbstractSQLDatabaseAccessor's. Pro: zero interference with main DB workload. Con: doubles connection footprint. - B. Share AbstractSQLDatabaseAccessor's DataSource; bump maximumPoolSize documentation guidance by +2. Pro: half the connection count. Con: a slow network poll could starve the main RTP workload. Recommendation: B, with maximumPoolSize docs bump. Confirm or override.

    Q3. Polling beyond N=32. At 1Hz poll, N=32 backends * 2 proxies = 64 reads/sec - still trivial for MySQL. At N=128 (rare but possible), it's 256 reads/sec, also fine. Recommendation: ship polling as-is; defer LISTEN/NOTIFY (Postgres) / Debezium-style streaming to a follow-up ADR. Confirm.

    Q4. Backend queueDepth field source. BackendHeartbeat has a queueDepth field. Most natural source is RegionQueueManager.keptLocations.size() + unkeptLocations.size(). But that's a region pool count, not a teleport-waitlist count. Recommendation: queueDepth = playerQueue.size() (the teleport waitlist), matching the REQ-RTP-NET-008 fairness metric. Confirm.

    Q5. Where does openBindingForType live? Either rtp-proxy-common exposes a static factory (NetworkBindings.open(NetworkConfig, DataSource)) consumed by both proxy adapter and RTPBukkitPlugin, OR each side wires its own. Recommendation: static factory in rtp-proxy-common - keeps the transport.type switch in one place.

    Q6. Module dependency direction. Backend-side wiring requires rtp-plugin to depend on rtp-proxy-common. Currently rtp-plugin -> rtp-core, and rtp-proxy-common -> rtp-api. Adding rtp-plugin -> rtp-proxy-common is acceptable (the dep is type-only - NetworkTransport, NetworkConfig, etc.). Alternative: move the SPI types into rtp-api and let both consume. Recommendation: add the dep - moving SPI to rtp-api exposes addon authors to proxy-shaped surfaces they don't need. Confirm.

    8. Risk surface¶

    • Moderate. New transport binding, new backend publisher, new resource file, new SPI default method (additive), modest edit to RTPBukkitPlugin. ~700-900 LOC across both modules.
    • Reversible. The default for network.enabled stays false; existing deployments see byte-identical behavior. REQ-RTP-NET-002 guard test is the safety net.
    • No S-00x exposure. No new chunk I/O, no main-thread blocking (BackendStatePublisher lives on its own daemon thread), no claim-plugin interactions.
