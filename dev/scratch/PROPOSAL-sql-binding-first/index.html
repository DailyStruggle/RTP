    PROPOSAL - SQL-First Network Binding (Phase 2b reframe; Redis becomes Phase 2e optimisation; proxy-as-participant is the default role)¶

    Status: Draft (design-only; no code in scope) Date: 2026-05-18 (rev 2 - participant default re-elevated per user direction "we designed both options to toggle between. Our first choice is proxy as a participant") Owner: session author Effective Issue: flip the architectural default back to proxy-as-participant (proxy holds a live NetworkStateBinding, publishes a heartbeat, can run the selector locally) while keeping proxy-as-router (thin: redeem-token-and-forward only) as a supported toggle. Both transport.type: sql and transport.type: redis remain peer bindings under the toggle. Supersedes (partial): docs/dev/scratch/PROPOSAL-velocity-redis-startup.md §11 (Phase 2b cut) and §1 framing of Lua scripts as Velocity-scoped. Refines: MULTI_SERVER_PLAN.md Phase 2 ordering; rtp-proxy-ADR-005 scope; rtp-proxy-ADR-006 boot-order step 10.

    1. Thesis¶

    Two orthogonal axes; v1 ships both as toggles and picks one as the default in each.

    Axis A - Transport binding (transport.type)¶

    • inMemory (dev/test only).
    • sql - shared SQL database that every backend already talks to (reuses AbstractSQLDatabaseAccessor).
    • redis - Lettuce-backed pub/sub + Lua atomic-claim. Lower latency; opt-in.

    Default for v1: sql. Redis is a latency optimisation, not a requirement. (See §3 for the SQL binding's shape; §4 for why Lua is scoped to the Redis binding only.)

    Axis B - Proxy role (proxy.role)¶

    • participant (default). The proxy holds a live NetworkStateBinding open just like any backend does. It publishes a ProxyHeartbeat via ProxyStatePublisher, can run BackendSelector#choose(...) locally against the current NetworkSnapshot, participates in network-wait-queue fairness, and originates /rtp requests as a first-class actor when a player is on the proxy with no current backend. Plan line 73 already names proxies as "ordinary participants" of the shared store - this default makes that explicit.
    • router. The proxy intercepts ServerPreConnectEvent, redeems a reservation token that some backend (or a hub backend running /rtp) already produced, mutates the connect target, and forwards. No selector on the proxy, no ProxyStatePublisher, no live subscriber thread. Lighter footprint; appropriate when a hub backend is doing all the heavy lifting.

    The toggle is implicit via wiring in the Velocity adapter, not a separate config knob: under participant the adapter registers ProxyStatePublisher + BackendSelector + transport subscriber; under router it skips those and only wires ServerPreConnectEvent. Both modes consume the same NetworkStateBinding SPI - the binding has no idea which role its caller is playing.

    What is shared state regardless of role¶

    The following live in the binding's authoritative store (DB tables for sql, Redis keys for redis) - never proxy-local memory, never proxy-to-proxy chatter (plan §Design rules line 77, hub-and-spokes star topology):

    • Region registry
    • Tokenized available-coordinate pool (the cross-network analogue of keptLocations/unkeptLocations)
    • Network wait queue (REQ-RTP-NET-008)
    • Backend heartbeats / load advertisement
    • Proxy heartbeats (proxy_state table, sketched in plan line 750) - written by participants, ignored by routers
    • Kill switch + schemaVersion gate (ADR-010)

    This means: switching proxy.role at runtime changes what the local proxy does, but does not change what other network members observe in the shared store - a router-mode proxy simply contributes less to the heartbeat table. Mixed-mode networks (one participant proxy + one router proxy) are well-defined.

    2. Phase 2 reordering¶

    Phase Was Becomes
    2b Velocity adapter + sender + publisher + Brigadier on InMemoryNetworkStateBinding Velocity adapter + sender + publisher + Brigadier + SqlNetworkStateBinding as the default production transport
    2c ServerPreConnectEvent + token redemption unchanged (still consumes NetworkStateBinding opaquely)
    2d Brigadier /rtp on proxy folded into 2b
    2e Redis transport adapter unchanged in scope, demoted in priority: opt-in performance binding, not the recommended default
    2f Regression + lite-jar exclusion lite-jar default transport.type: sql (closes open Q5)

    3. SqlNetworkStateBinding shape¶

    Implements NetworkTransport + acts as the network-state member on AbstractSQLDatabaseAccessor (the slot landed in Phase 1). Tables (one per concern, names indicative, all carry schemaVersion):

    • rtp_network_backends(backend_id PK, world_set, last_heartbeat_at, mspt_p95, tps_1m, load_score, capacity, alive)
    • rtp_network_locations(token PK, backend_id FK, world, x, y, z, produced_at, claimed_at NULL, claimed_by NULL, expires_at)
    • rtp_network_wait_queue(seq PK auto, player_uuid UNIQUE, enqueued_at, network_id)
    • rtp_network_control(network_id PK, kill_switch BOOL, min_schema_version INT, updated_at)

    Operations map 1:1 to existing NetworkTransport SPI methods:

    • publishBackendHeartbeat(...) -> UPSERT rtp_network_backends.
    • subscribeBackendHeartbeats(sink) -> polled SELECT on a scheduler tick (configurable interval, default 1s), diffed against last snapshot; sink invoked on change.
    • claimReservationToken(...) -> single-statement UPDATE rtp_network_locations SET claimed_at=..., claimed_by=... WHERE token=? AND claimed_at IS NULL RETURNING .... Atomic on every backend (MySQL 8.0+, Postgres, SQLite via BEGIN IMMEDIATE, H2 via MERGE).
    • releaseReservationToken(...) -> UPDATE ... SET claimed_at=NULL WHERE token=? AND claimed_by=?.
    • Orphan reanimation -> a scheduled sweep on every binding: UPDATE ... SET claimed_at=NULL, claimed_by=NULL WHERE claimed_at IS NOT NULL AND claimed_at + ttl < now(). Identical semantics to ADR-005's Lua sweeper; just slower and bus-friendly.

    Determinism guarantee for REQ-RTP-NET-013: every backend reads the same rtp_network_backends snapshot at the same heartbeat tick (within polling skew). WeightedAverageBackendSelector is already deterministic over a snapshot, so the same input -> same decision on every JVM.

    4. Lua scripts: scoped to RedisNetworkStateBinding, not Velocity¶

    Correction to PROPOSAL-velocity-redis-startup.md §1 step 10d:

    • SCRIPT LOAD for atomic claim + sweeper-reanimate moves from "Velocity startup step 10d" to "RedisNetworkStateBinding.open() lifecycle step". Velocity's boot calls transport.open(); whatever the transport needs to do internally is opaque to Velocity.
    • The same Lua scripts (and the same EVALSHA invocations) are reused by backend-side callers when a Bukkit/Paper/Folia plugin holds the binding for a backend-originated claim. There is nothing proxy-specific about them.
    • Structural fix in the original proposal: split §1 into two tables - (i) Velocity bootstrap steps (transport-agnostic: 1-9, 11-19), (ii) RedisNetworkStateBinding.open() steps (10a-10e). The Redis table is then reused verbatim by any backend-side caller.

    Do we need Lua at all? Yes, but only for RedisNetworkStateBinding. Both scripts (atomic claim, orphan sweep) collapse 2-3 round-trips into one and give strict atomicity that vanilla WATCH/MULTI/EXEC can't match cleanly on Dragonfly/KeyDB. Cost: one SCRIPT LOAD per open(), one EVALSHA per claim. Negligible.

    SqlNetworkStateBinding does not use Lua - it uses the database's native atomic-update semantics.

    5. Config implications (network.yml, ADR-002)¶

    • transport.type enum gains sql (existing: inMemory, redis).
    • transport.sql.dataSource -> name of an existing entry under the plugin's database config (we reuse AbstractSQLDatabaseAccessor's connection pool; no new HikariCP setup).
    • transport.sql.heartbeatPollMs -> default 1000.
    • transport.sql.tableNamePrefix -> default rtp_network_.
    • Lite-jar default: transport.type: sql (was open Q5 in the original proposal).

    ADR-002 is Accepted. Adding the sql enum value is a forward-compatible schema bump (covered by schemaVersion negotiation); not a re-acceptance event.

    6. What this does NOT change¶

    • rtp-proxy-common SPI surface: zero changes. SqlNetworkStateBinding is just another implementation, peer to InMemoryNetworkStateBinding. proxy.role is an adapter-side wiring decision, not an SPI concept - the binding has no role parameter.
    • rtp-proxy-velocity Phase 2a (already shipped): unchanged. The no-op shell is still correct under both roles (network.enabled:false short-circuits before role resolution).
    • ADR-005 / ADR-010: still Proposed. This proposal does not flip either. ADR-005 stays scoped to the Redis binding (good as written); ADR-010's HMAC discussion applies to any wire transport (Redis), not to the SQL binding (where the DB connection's own auth and TLS replace HMAC). The participant/router distinction is orthogonal to both ADRs.

    7. Open questions¶

    1. Heartbeat polling overhead. A 1s poll on rtp_network_backends from N backends is N SELECTs/sec network-wide. Acceptable for N <= 32; needs LISTEN/NOTIFY (Postgres) or trigger-based fan-out for larger. Defer to ADR if it becomes a problem.
    2. SqlNetworkStateBinding on SQLite. Single-writer; works for tiny networks (1-2 backends sharing a file) but not realistic for proxy-fronted networks. Document as "MySQL/Postgres recommended; SQLite for dev/test only".
    3. HikariCP pool sizing. Network-mode traffic is additive to existing plugin DB traffic. Should the binding own its own small pool, or share the accessor's pool? Recommended: share (one less moving part), but raise maximumPoolSize documentation guidance by +2.
    4. Replay resistance without HMAC. SQL binding leans on DB connection auth + TLS; ADR-010's replay-nonce discussion is N/A. Document this explicitly so ops don't expect the same wire-level protections.

    8. Verdict¶

    Adopt this reordering. Concretely:

    1. Amend MULTI_SERVER_PLAN.md Phase 2 ordering per §2 above; add a one-paragraph Proxy roles subsection naming participant as the default and router as the lightweight toggle, citing §1 Axis B of this proposal.
    2. Amend PROPOSAL-velocity-redis-startup.md §1 to split the table per §4 above (Velocity steps vs RedisNetworkStateBinding.open() steps), and §11 to point Phase 2b at SqlNetworkStateBinding with proxy.role: participant as the default wiring path.
    3. Author a new subproject ADR rtp-proxy-ADR-011-sql-network-state-binding.md (Proposed) holding §3 + §5 + §7 of this proposal. ADR-005 stays untouched.
    4. Author a second subproject ADR rtp-proxy-ADR-012-proxy-role-participant-default.md (Proposed) holding §1 Axis B of this proposal: the participant/router toggle, the default selection, the implicit-via-wiring implementation, and the mixed-mode-network well-definedness claim.
    5. Land code in a follow-up D-005 turn (still gated).

    No source changes in this turn. Recommended next D-005 turn: ratify steps 1-4 above (still docs-only), then schedule the Phase 2b code cut.
