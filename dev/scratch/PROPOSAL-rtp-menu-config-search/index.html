    PROPOSAL: rtp menu config search¶

    Status: DRAFT, awaiting explicit user approval (Rule D-005). Author: Junie session 2026-05-19. Effective Issue: "A user had difficulty tracing a specific message. We should add a search option to our config stuff in rtp menu ... start with the rtp menu command ... cast off color for the text search otherwise it will be unusable with gradients."

    1. Goal¶

    Add a first-class search entry to the rtp menu config flow that lets an operator find any config key or value across every loaded config file by typing a free-form substring, and jumps from each hit to the existing per-key config menu page.

    The motivating use case: an admin sees a message in chat (e.g. "You are not allowed to RTP here.") and wants to know which messages.yml key produced it without grepping the jar.

    2. User-confirmed constraints (this session)¶

    1. Search spans all config files at once (not a single file).
    2. Search matches both keys and values (comments excluded; the user explicitly noted "if we ignore comment lines" the corpus is small).
    3. Case-insensitive substring match.
    4. No result cap ("the sum of config files aren't that big").
    5. Render hits as a multi-page book, one row per hit, clickable to open the existing config-key page that manages that file/key (reuses MenuAction.OpenConfigKey).
    6. Visual: gray base text with off-blue highlight on the matched substring.
    7. Search must operate on color-stripped text for both the haystack and the needle. Legacy &/§ codes, modern hex (&#rrggbb) and gradient spans must NOT break substring matching. Highlight runs are computed against the stripped form and projected back onto raw offsets.
    8. Display the raw (un-rendered) text in each result row, not the colorized rendering (user update 2026-05-19: "we can display the raw text to the user so they know they can add or remove colors"). Operators must be able to see every &a, §l, &#rrggbb, gradient tag, etc. that is actually present in the config so they know what color codes exist and can decide to add or remove them. The off-blue highlight is overlaid on top of that raw text at the projected raw-offset ranges from §2.7. This is a deliberate departure from the file-view page (which renders colors) — search results are an editing aid, not a preview.
    9. Entry point: a search button on the config selector page plus an anvil-input prompt for the query string (same mechanism PromptAnvilInput already uses for param pickers).

    4. Before / after¶

    Before: /rtp menu config opens a selector page. Each row is a config file; clicking opens that file's keys. To find the source of a specific message, the operator must page through messages.yml manually or grep the jar.

    After: /rtp menu config selector gains a "Search" button at the top. Clicking it opens an anvil input prompt titled "Search all configs". On submit, OpenConfigSearchResults(query, 0) is redeemed; the renderer shows a paginated book of all hits across every loaded config. Each row shows the raw, literal text of the value (color codes visible as-is) so the operator can see what formatting is in place and decide whether to add or remove codes — the off-blue highlight overlays the matched substring at its projected raw offsets:

    [messages.yml] notPermitted           = &7You are not allowed to RTP &9&lhere&7.
[messages.yml] menuInvalid            = &7Unknown menu command: &9&lsearch&7
[regions/default.yml] biome.whitelist  = &#7f7f7fplains, &9&lforest&7, jungle

    The literal &7, &9&l, &#7f7f7f, etc. are displayed as text, not interpreted as color. The substring here / search / forest is rendered in the off-blue accent color (on top of the raw text); everything else in the row is the menu's gray base color. Each row is clickable; clicking jumps straight to the existing per-key config menu page (the same page /rtp config <file> view -> click-on-row already opens). Back button returns to the search-results page; another Back returns to the selector.

    5. Threading / safety¶

    • All config reads happen on the dispatching thread inside the existing MenuRedeemSubcommand async pipeline (no main-thread chunk I/O — S-005 unaffected).
    • The new dispatch arms gate on permission rtp.config and on senderId != null (consistent with the other OpenConfig* arms).
    • Token registry: each result page render mints a fresh OpenConfigSearchResults(query, page) token for prev/next, and one OpenConfigKey(file, key) token per result row. Existing TTL / per-player isolation rules apply; no new registry primitives.
    • No DB or chunk allocations; MemoryTracker unaffected.

There is no carried next-action descriptor.

    Implication for this feature: the proposed OpenConfigSearchPrompt action cannot reuse PromptAnvilInput as-is. Two viable shapes: - (A) Mint the prompt as PromptAnvilInput(parentPath=["menu","config","search"], paramName="query", prefill="") and have the menu config search subcommand (a thin new TreeCommand leaf under MenuRedeemSubcommand) accept query:<text>, build the results model itself, and hand it to the renderer. This piggybacks on the existing pipeline (/rtp menu config search query:foo) and adds zero new menu-action variants on the prompt side — only OpenConfigSearchResults(query, page) remains needed for pagination + the selector-button entry. Preferred. - (B) Add a small extension to PromptAnvilInput (or a sibling variant PromptAnvilInputThen(parentPath, paramName, prefill, MenuAction continuation)) so the post-submit action is carried by the prompt itself.     7. Risks and trade-offs¶

    • Sealed MenuAction churn: every addition to MenuAction is an API event for addons that pattern-match on it. The two new records are additive and the existing sealed-shape test exists precisely to flag this; addons that use exhaustive switch on MenuAction will get an unhandled-arm warning. Acceptable; document in CHANGELOG.md under the next unreleased version.
    • Color-strip correctness: gradient/hex codes have several syntaxes in this codebase (legacy &x, §x, &#rrggbb, and the MiniMessage carry-over). Getting the strip wrong silently breaks highlight projection (highlight appears on the wrong characters). Mitigation: dedicated unit tests for the strip helper covering each syntax, plus a test that feeds a known gradient-wrapped value through ConfigSearchResultsBuilder and asserts the highlight offsets land on the correct raw characters.
    • Very short queries: a 1-char query would match almost everything. Mitigate with a minimum-length guard (proposed: >= 2 chars) backed by menuConfigSearchTooShort locale string. If the user disagrees, drop the guard.
    • Per-world regions.yml duplication: a value present in 10 region overrides will produce 10 hits. Acceptable for v1 (the operator wants to know all the places); revisit if it becomes noisy.
    • No result cap: the user explicitly waived the cap. A pathological config (huge worlds.yml with thousands of override values) could produce a multi-hundred-page book. Acceptable; the book renderer already paginates and the cost is bounded by total config size which is small.

    Key English baseline
    menuConfigSearchButton &9Search all configs

    menuConfigSearchEmpty &7No matches for &f[query]&7.

    Highlight is applied by the renderer post-format, not encoded in the locale string (so translators don't have to think about color spans). The off-blue color used for the highlight is the existing menu accent color (resolve from the menu theme; do not hardcode a hex).

    11. Out of scope¶

    • Searching comments (explicitly excluded per the user's "if we ignore comment lines" remark).
    • Regex / fuzzy / token-aware search. v1 is plain case-insensitive substring.
    • Cross-server search over the proxy network (proxy-aware search is a future item if it ever surfaces; not currently requested).
    • A /rtp config search <query> chat command. The menu+anvil-input path is the only entry surface; if a non-menu entry is needed later, it can be added as a thin wrapper that mints the same OpenConfigSearchResults action.
