    PROPOSAL — Metrics-to-Maps: declarative ChartSpec bridging MetricsSnapshot to MapBinding¶

    Status: Draft, awaiting D-005 approval. Authored: 2026-05-20. Mode at authorship: [CODE] (drafted as docs-only per D-005 — no source files touched). Effective Issue (latest, 2026-05-20): "great let's make it, first wiring in maps into our menu info system using a drawing of bad points in the region then move on to metrics integration."

    1. Summary¶

    Add a declarative bridge so RTP can:

    1. Build a ChartSpec from a typed admin request (kind + source + region/window/viewer/tile-grid).
    2. Resolve that spec against existing in-memory state (MemoryShape bad-locations, MetricsSnapshot, ADR-039 SurfaceModel data) on a worker thread, producing a sealed ChartModel (maps-api).
    3. Hand the ChartModel to the active ChartRenderer<M> and MapBinding to paint the result onto a cartography map.
    4. Surface the resulting map as a click-action from the existing /rtp info menu (ADR-035 / ADR-044), via a new MenuAction kind (e.g. OPEN_MAP).

    The two halves already exist: - Data side — metrics-api MetricsSnapshot + MemoryShape.addBadLocation + ADR-039's planned DiagnosticSurface / SurfaceModel. - Pixel side — maps-api MapBinding SPI + sealed ChartModel permits + HeatmapRenderer + NoopMapBinding.

    What does not exist: any orchestrator that names a chart declaratively and routes the result through the menu. This proposal adds exactly that, without widening any data contract and without introducing new I/O hotpaths.

    This is the connector ADR-046 / ADR-039 / ADR-040 each implicitly assume but none authors.

    2. Two-stage rollout (mirrors the Effective Issue)¶

    The user's update explicitly orders the work: first menu→map for "bad points in the region"; then broader metrics integration. Both stages share the same ChartSpec machinery so Stage 2 reduces to adding new spec kinds and new resolvers.

    Stage 1 — Bad-points heatmap from /rtp info (target)¶

    • New menu entry under /rtp info (administrator subtree, gated on rtp.admin.diag or equivalent existing permission — to be confirmed against RtpAdminPermissions):
    • Label: configurable via messages.yml key menuInfoBadPointsLabel (REQ-RTP-F-013, S-007).
    • Click action: OPEN_MAP (new MenuAction.Kind), payload = serialized ChartSpec(kind=BAD_POINTS_HEATMAP, region=<active>, viewer=<player UUID>, tiles=1x1).
    • On click, rtp-core resolves the spec on the existing async scheduler:
    • Reads MemoryShape.badKeysCache (already populated and persisted; no new I/O).
    • Decodes each 1D spiral index via Shape.locationToXZ.
    • Buckets into a fixed-resolution grid (default 128×128 to match MapCanvas.VANILLA_WIDTH/HEIGHT; tileGrid may multiply).
    • Normalises to a Heatmap2D(width, height, double[] counts, 0, max).
    • Hands the model to the installed MapBinding.allocate(...) then renderEphemeral(handle, HeatmapRenderer, model). The map item is given to the requesting admin.
    • Configurable failure messages (S-007): mapBusy, mapUnavailable, mapBindingMissing keyed under messages.yml per REQ-RTP-F-013.

    Stage 2 — Broader metrics integration¶

    Add resolvers and ChartSpec.Kind values for the remaining ADR-039 surfaces — each one is a single resolver class plus a MenuAction.OPEN_MAP entry in the existing diagnostic menu. No new platform code.

    ChartSpec.Kind Resolver source ChartModel produced Renderer
    BAD_POINTS_HEATMAP MemoryShape.badKeysCache Heatmap2D HeatmapRenderer (exists)
    REGION_COVERAGE RegionQueueManager.keptLocations / unkeptLocations / backlogLocations RegionCoverage RegionCoverageRenderer (new, Stage 2)
    FAIL_RATE_HEATMAP ADR-039 FailHeatSnapshot ring buffer Heatmap2D HeatmapRenderer
    CACHE_OCCUPANCY RegionQueueManager size getters CategoryDistribution CategoryPieRenderer (new, Stage 2 — already in CHECKLIST-maps-api.md 4.1)
    METRIC_SPARKLINE ADR-039 in-memory ring on MetricsSnapshot keys TimeSeries SparklineRenderer (new, Stage 2 — already in CHECKLIST-maps-api.md 4.2)

    Stage 2 is gated on ADR-039's SurfaceModel types actually being authored (currently paper) and maps-api Stage 2 (BukkitMapBinding + RTPHooks slot) landing.

    3. Affected modules and proposed structure¶

    3.1 New types¶

    Module New file Purpose
    rtp-api menu/MenuAction.java (extend) Add Kind.OPEN_MAP and a chartSpecId(String) payload field. No new behaviour on existing kinds.
    rtp-api maps/ChartSpec.java Sealed record carrier: Kind, String regionName, @Nullable UUID viewer, int tilesRows, int tilesCols, optional String metricKey, int windowSeconds. Renderer-neutral. Pure data; no platform / maps-api imports.
    rtp-core commands/maps/ChartSpecResolver.java Interface: CompletableFuture<ChartModel> resolve(ChartSpec, RTPCtx ctx). Strict S-005 contract: must not call world.getChunkAt synchronously; must not block on Future#get/#join.
    rtp-core commands/maps/resolvers/BadPointsHeatmapResolver.java Reads MemoryShape.badKeysCache, decodes via Shape.locationToXZ, buckets to Heatmap2D. Pure CPU.
    rtp-core commands/maps/MapDispatch.java Single entry point invoked by the OPEN_MAP MenuAction handler in rtp-plugin. Selects resolver, awaits the model (off-thread), then calls MapBinding.allocate + renderEphemeral via the supplied HeatmapRenderer. Configurable failure messages route through RTP.log (S-004) and sendMessage keyed on messages.yml.

    rtp-core depends on maps-api for the ChartModel / ChartRenderer / MapBinding types only. It does not depend on mapsapi.render.. (enforced by an ArchUnit rule added to the existing module-wide guard in ReqRtpMap002NoChunkIoTest — extended scope, no new test class).

    3.2 Edited types (minimal)¶

    Module File Edit
    rtp-api menu/MenuAction.java New enum constant + sealed-permits guard or constructor branch (preserves backwards compat).
    rtp-plugin bukkit/commands/info/InfoCmd*.java (or wherever the admin /rtp info page is composed) Append one MenuLine with MenuFragment(text=…, action=MenuAction.openMap(chartSpecId)).
    rtp-plugin bukkit/menu/<dispatch wiring>.java Map MenuAction.Kind.OPEN_MAP → MapDispatch.

    No edits to MetricsSnapshot, Metrics, MetricsBinding, or any sampler. No edits to MemoryShape beyond exposing a read-only iterator of bad-location indices (it may already suffice via the existing public methods — confirm in Stage 1 step 1 before adding any accessor). No edits to maps-api SPI.

    3.3 Not in scope of this proposal¶

    • BukkitMapBinding / FoliaMapBinding / FabricMapBinding themselves. They are the parallel CHECKLIST-maps-api.md Stage 2 / Stage 3 work. This proposal assumes BukkitMapBinding lands first (or in lockstep); without it MapDispatch resolves to NoopMapBinding and surfaces the configurable mapBindingMissing message.
    • Live-streamed charts. MapBinding.bindLive is not used in Stage 1. renderEphemeral only. Live binding is a Stage 2+ option.
    • Persisting charts across restarts. Charts are one-shot per admin request.
    • Mermaid (MermaidChart / Stage 4.4 of CHECKLIST-maps-api.md). Unrelated.

    4. Relevant REQs / ADRs¶

    • REQ-RTP-MAP-001..005 — maps-api REQs already cover require-by-contract, no chunk I/O, lifecycle, Lite-only Noop, Mermaid subset. This proposal adds no new REQ unless approval includes a new REQ-RTP-OBS-N for "diagnostic surfaces shall be renderer-pluggable".
    • REQ-RTP-OBS-001 — non-blocking metrics snapshot. The resolver chain is strict consumer of MetricsSnapshot; no new writes, no new schema. Preserved.
    • REQ-RTP-F-013 / S-007 — every user-facing string (menuInfoBadPointsLabel, mapBusy, mapUnavailable, mapBindingMissing) is keyed in messages.yml (new locale rows mirrored per Locale Parity Maintenance — TSV pipeline).
    • REQ-RTP-S-004 — no silently-discarded failures. Every MapDispatch exit path either delivers the model, surfaces a configurable message, or RTP.log(Level.WARNING, …).
    • REQ-RTP-S-005 — no chunk I/O on the main thread. BadPointsHeatmapResolver reads only in-memory state (MemoryShape.badKeysCache). Resolver chain runs via RTP.scheduler.runTaskAsynchronously on Bukkit/Paper, runTaskTimerAsynchronously on Folia (per existing scheduler abstraction).
    • REQ-RTP-S-006 — MapBinding API throws IllegalStateException before core loads. Preserved by routing through the existing RTPHooks MapBinding slot (added in CHECKLIST-maps-api.md Stage 2.6).
    • ADR-035 — menu framework. This proposal extends MenuAction with a new kind; no other change.
    • ADR-039 — diagnostic surfaces. The Stage 2 resolvers consume the same SurfaceModel types ADR-039 plans (still paper). This proposal does not require ADR-039 to be amended; it positions MapBinding as a renderer peer to MenuRenderer for the same surfaces.
    • ADR-044 — command-tree menu reflector. The admin /rtp info page is already composed via the reflector; we add one curated fragment.
    • ADR-046 — maps-api module. This proposal is the natural next step after CHECKLIST-maps-api.md Stage 2. No amendment required unless approval wants a ChartSpec re-export under rtp-api/.../maps/.
    • D-005 — this document is the proposal.

    A new ADR — call it ADR-047 — Declarative Chart Composition Bridge — is the proposed governance artifact. It can either land alongside this proposal's approval or be authored after Stage 1 ships, mirroring how ADR-035 followed CHECKLIST-generalized-menu.md Stage 1. Recommend authoring up-front since the surface touches three SPIs (menu, maps, metrics).

    5. Risks and trade-offs¶

    Risk Mitigation
    MapBinding not yet installed on any platform → every OPEN_MAP click fails. Surface the configurable mapBindingMissing message; gate the menu entry on MapBinding != NoopMapBinding so admins don't see a dead link. Same pattern as the existing MenuRenderer selector in RTPCmdBukkit#selectMenuRenderer.
    MemoryShape.badKeysCache is large on long-running servers; bucketing 100k+ indices to a 128×128 grid is CPU-bound. Resolver runs off-thread; counts are accumulated in a primitive long[16384]. Worst case sub-10 ms on commodity hardware. Cap input read to Math.min(cache.length, BAD_POINTS_RESOLVER_CAP) with a configurable cap defaulting to 250k.
    Adding Kind.OPEN_MAP to MenuAction is a model-shape change visible to every MenuRenderer. BookMenuRenderer and the test renderers already iterate MenuAction defensively; new kinds without a handler fall back to inert text (verified by MenuStageTwoTest.openPageRejectsWithMenuInvalidWhenRendererThrows). Add one test asserting BookMenuRenderer does not throw on OPEN_MAP.
    Stage 2 metrics resolvers race the ADR-039 SurfaceModel work. Stage 2 is explicitly gated on ADR-039 surfaces being authored. Stage 1 only depends on MemoryShape and maps-api Stage 2 — both already on track.
    Locale parity drift when adding menuInfoBadPointsLabel, mapBusy, etc. Follow Locale Config TSV Pipeline: edit baseline messages.yml, locale-files-to-csv → reconcile-locale-csvs → translate → locale-files-from-csv → LocaleParityTest.
    rtp-core depending on maps-api types creates a new module edge. Already a one-way edge documented in CHECKLIST-maps-api.md row 129 ("RegionCoverage model wiring … is the only place where rtp-core reaches into maps-api"). This proposal extends that edge to include ChartModel, MapBinding, and ChartRenderer types only — no mapsapi.render.. import. ArchUnit rule extends to enforce.

    6. Stage-1 acceptance criteria (for the Stage-1 PR alone)¶

    1. Running .\gradlew :rtp-plugin:run (or equivalent dev server) and issuing /rtp info shows the new "Bad points map" line for an admin.
    2. Clicking it (or running the equivalent /rtp menu redeem <token> flow) emits a single 128×128 cartography map filled with the bad-points heatmap rendered via HeatmapRenderer. The map is given to the requesting player's inventory.
    3. With MapBinding == NoopMapBinding, clicking surfaces the configurable mapBindingMissing message; nothing is logged at SEVERE; one WARNING is logged via RTP.log per REQ-RTP-S-004.
    4. New tests green:
    5. BadPointsHeatmapResolverTest (pure unit; 4 cases: empty cache, single point, 4-quadrant spread, cap enforcement).
    6. MapDispatchTest (3 cases: happy / NoopMapBinding / resolver throws → routed through configurable message).
    7. MenuActionOpenMapBackcompatTest (asserts existing BookMenuRenderer ignores unknown action kinds without throwing — regression guard for the model-shape change).
    8. LocaleParityTest green after the TSV pipeline runs.
    9. .\gradlew build green (per Final Full Build rule).
    10. TRACEABILITY.md row(s) updated if any new REQ-* added (default: none).
    11. CHANGELOG.md bullet under the current unreleased version.

    7. Out-of-scope follow-ups (Stage 2 onward — separate checklists / PRs)¶

    • Stage 2 ChartSpec kinds (REGION_COVERAGE, FAIL_RATE_HEATMAP, CACHE_OCCUPANCY, METRIC_SPARKLINE) — each one is a single resolver class, a single test, and a MessagesKeys entry. Land in the same order ADR-039's surfaces land.
    • Live charts via MapBinding.bindLive — only after Stage 1 + Stage 2 prove the static path is correct on Bukkit/Paper/Folia.
    • Cross-backend --backend <id> on OPEN_MAP once ADR-040's network snapshot publishes the relevant rows. Out-of-scope here.
    • Fabric MapBinding (Stage 3 of CHECKLIST-maps-api.md). Gated on Fabric stabilising.

    8. Requested approval (D-005)¶

    Three explicit go/no-go items needing user sign-off before I write any source:

    1. Approve the scope of Stage 1 exactly as described in §2 (bad-points heatmap from /rtp info, single-tile, ephemeral, Bukkit/Paper first).
    2. Approve the ChartSpec placement in rtp-api/.../maps/ (vs. keeping it in rtp-core and re-exporting later). The proposal recommends rtp-api since addons may want to author specs.
    3. Approve authoring ADR-047 — Declarative Chart Composition Bridge up-front (before Stage 1 code), to lock the connector contract.

    If any of the three should be different, say so in the next <issue_update> and I will revise this proposal before opening any code path.
