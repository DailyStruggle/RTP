    Fabric Parity TODO (pre-Modrinth-publish)¶

    Status: scratch / working notes (gitignored under docs/dev/scratch/). Source conversation: 2026-05-19, scoping Fabric parity work before lite-v1.0.0 Modrinth publish. Author: drafted by Junie at user request; not canonical until promoted to MULTI_PLATFORM_PLAN.md or an ADR.

    Goal¶

    Reach lite-edition Fabric parity before the first lite-v* Modrinth publish so the listing can advertise fabric as a supported loader honestly. Full Pro parity is the eventual goal (per user: "lite is a version of Pro with fewer shown configuration options and fewer dependencies shaded in"), but is not a Modrinth blocker and can be sequenced after publish.

    Corrected baseline (2026-05-19)¶

    The AGENTS.md Current Development Focus bullet listing three Fabric blockers ("S-005 violation in FabricWorld.getChunkAt; null stub in FabricServerAccessor.getLocationGenerator; unresolved Loom dependency") is partially stale. Per user confirmation, Fabric is already running in practice, so the Loom dependency is resolved. The remaining two items still need verification. AGENTS.md and MULTI_PLATFORM_PLAN.md should be updated as part of Phase E below.

    Scope: lite vs Pro parity¶

    Per user: lite differs from Pro only in (a) which config options are shown to the operator and (b) which dependencies are shaded into the jar. There is no per-feature code fork between lite and Pro - both build from the same source tree against :rtp-plugin, lite via the lite assembly classifier (ADR-024). Therefore "lite parity" = "Pro parity minus shaded SQL/Redis drivers and minus Folia-only code paths."

    Folia is intentionally Pro-only and not relevant to Fabric parity (Folia is an MC server fork, not a mod loader; the two never co-exist).

    Phase A - Loom build verification (DROPPED)¶

    Originally proposed but resolved already per user. No action needed beyond noting it in Phase E's doc cleanup.

    Phase B - S-00x violation verification & fix¶

    B1 - FabricWorld.getChunkAt (S-005)¶

    • [ ] B1.1 Open platforms/rtp-fabric/rtp-fabric-common/src/main/java/.../FabricWorld.java, locate getChunkAt, confirm whether the synchronous chunk load is reachable from a main-thread path or has already been refactored.
    • [ ] B1.2 If still synchronous: refactor to return CompletableFuture<Chunk> (or equivalent async abstraction) consistent with how PaperWorld / FoliaWorld handle it.
    • [ ] B1.3 Add a regression test along the lines of ReqRtpS005ChunkLoadingTest but in rtp-fabric test sources. Reference REQ-RTP-S-005 in the class name or @DisplayName.
    • [ ] B1.4 Update docs/dev/TRACEABILITY.md REQ-RTP-S-005 row with the new test.

    B2 - FabricServerAccessor.getLocationGenerator (S-006)¶

    • [ ] B2.1 Open platforms/rtp-fabric/rtp-fabric-common/src/main/java/.../FabricServerAccessor.java, locate getLocationGenerator, confirm whether it still returns null or has been fixed.
    • [ ] B2.2 If still null: replace the null return with throw new IllegalStateException("RTP core not loaded; addon called API too early") per S-006.
    • [ ] B2.3 Add a regression test (e.g. ReqRtpS006FabricLocationGeneratorTest) asserting the IllegalStateException is thrown on pre-init access.
    • [ ] B2.4 Update docs/dev/TRACEABILITY.md REQ-RTP-S-006 row with the new test.

    Phase C - feature parity sweep (lite-relevant features only)¶

    Each item: verify the feature works on Fabric runtime; implement the gap if it doesn't. Each is its own [CODE] session.

    C1 - core teleport pipeline¶

    • [ ] C1.1 /rtp from a vanilla Fabric world succeeds end-to-end (shape -> chunk -> vert -> biome -> safety).
    • [ ] C1.2 MemoryTracker registers and releases on every exit path (success, failure, disconnect mid-teleport).
    • [ ] C1.3 No S-005 violations in logs (ReqRtpS004NullChunkAttributionTest-style guard equivalent).
    • [ ] C1.4 No printStackTrace(); all errors routed through RTP.log (S-004 audit).

    C2 - multilingual / /rtp lang (ADR-020)¶

    • [ ] C2.1 LanguageBootstrap.resolve(pluginDirectory) finds lang/** from the Fabric mod's resource path.
    • [ ] C2.2 /rtp lang <locale> switches the locale at runtime on Fabric.
    • [ ] C2.3 LocaleParityTest still green after any Fabric-specific resource-loading changes.

    C3 - claim integrations (ADR-019 amendment)¶

    • [ ] C3.1 Confirm no claim plugin softdepends fire on a Fabric runtime (claim plugins are Bukkit-only).
    • [ ] C3.2 Verify the integration layer no-ops cleanly without NPE when no claim plugin is present.
    • [ ] C3.3 If any claim plugin has a Fabric port (HuskTowns has one), audit whether the integration should be enabled there - record findings in docs/dev/EXTERNAL_HOOKS.md.

    C4 - anvil pre-filter (ADR-016)¶

    • [ ] C4.1 Confirm .mca file path resolution works on Fabric's world layout (world/region/, world/DIM-1/region/, etc.).
    • [ ] C4.2 Run anvil-prefilter-enabled /rtp end-to-end; verify biome/material checks succeed without loading chunks.
    • [ ] C4.3 No surprises with Fabric's world-dimension naming vs Bukkit's.

    C5 - effects / events bridges (existing partial work)¶

    • [ ] C5.1 Audit FabricEventBridge for completeness against the Paper/Bukkit event surface.
    • [ ] C5.2 Audit FabricOnEventTeleports against BukkitOnEventTeleports for missed event types (firstjoin, join, death, respawn, void).
    • [ ] C5.3 Audit FabricEffectsHandlerUnobf (and the obf carrier sibling) for parity with BukkitEffectsInitializer / BukkitValueCoercer.

    C6 - personal queue / per-player buckets (ADR-043)¶

    • [ ] C6.1 Verify openPersonalQueue / closePersonalQueue lifecycle fires on Fabric login/logout events.
    • [ ] C6.2 rtp.personalqueue opt-in semantics work identically to Bukkit.

    C7 - commands¶

    • [ ] C7.1 Brigadier bridge (BrigadierCommandAdapter, BrigadierBridgeContext) wired on Fabric per commands-api-ADR-001.
    • [ ] C7.2 Every lite-relevant /rtp subcommand parses, tab-completes, and executes on Fabric.
    • [ ] C7.3 Permission checks honored on Fabric (LuckPerms-Fabric or equivalent).

    Phase D - cross-version smoke test¶

    • [ ] D1 Boot rtp-fabric-v1_20_R1 against a matching Fabric Loader + MC version; run /rtp 10x; verify no errors in logs.
    • [ ] D2 Same for rtp-fabric-v1_21_R1.
    • [ ] D3 Same for rtp-fabric-v1_21_R5.
    • [ ] D4 Same for rtp-fabric-v1_21_R11.
    • [ ] D5 Same for rtp-fabric-v26_1_R1 (the deobf MC 26.x carrier).
    • [ ] D6 Document the smoke-test procedure (steps, expected output, common failure modes) as either a permanent docs/dev/FABRIC_SMOKE_TEST.md or, if it stays one-off, leave inline in this scratch file.

    Phase E - publish surface + doc cleanup¶

    • [ ] E1 Add fabric to the loaders: list in .github/workflows/release.yml.
    • [ ] E2 Update CHANGELOG.md under the relevant unreleased section: remove the "Fabric is planned" caveat, list Fabric as shipped, name the MC versions covered. (There is no separate CHANGELOG-lite.md; tag any Pro-only bullet with **(Pro)** per the rule at the top of CHANGELOG.md.)
    • [ ] E3 Update docs/dev/MULTI_PLATFORM_PLAN.md Phase 4 status to "complete" (or whichever stage label applies).
    • [ ] E4 Update .junie/AGENTS.md Current Development Focus: retire Fabric from "active frontier" status, drop the three stale-blocker bullet, point readers at the new stable state.
    • [ ] E5 If rtp-fabric-ADR-002 (platform-in-scope) needs a closing amendment, add one stating parity is reached.

    Out of scope for this checklist (deferred past Modrinth publish)¶

    • Full Pro Fabric features: SQL/Redis persistence on Fabric runtime, login reserve cache wiring on Fabric, visitor mode on Fabric, advanced performance.yml toggles on Fabric. These ship to BBB Pro and do not gate the Modrinth lite publish.
    • bStats on Fabric (tracked in MULTI_PLATFORM_PLAN.md, row metrics = new Metrics(this, 30865)). Possible but not yet wired: no official bstats-fabric artifact, so do it via a shaded/community bStats Metrics/MetricsBase copy or a small custom submitter to the bStats v2 data endpoint on an RTP.scheduler async timer, registering RTP's chart catalogue through metrics-api (MetricsSnapshot / FabricMetricsBinding). rtp-fabric-only; D-005 gated. Not a Modrinth-publish blocker.
    • Forge / NeoForge support (Phase 5+ per MULTI_PLATFORM_PLAN.md, out of scope until Fabric stabilizes).
    • Cross-server proxy support on Fabric (independent axis per MULTI_SERVER_PLAN.md).

    Ordering recommendation¶

    Run phases sequentially: B (safety blockers) -> C (feature sweep) -> D (smoke test) -> E (publish surface + docs).

    Within Phase C, the items are mostly independent except C1 which is foundational; do C1 first, then C2-C7 in any order. C5 (effects/events) is the most likely to surface real bugs because it has the most existing partial work.

    Within Phase B, B2 is trivial and can be done first as a warm-up. B1 is the substantive safety fix.
