    PROPOSAL: MultiConfig submenu (regions, worlds, future kinds) for the runtime book menu¶

    Status: Proposal (this file). Author: Junie, 2026-05-22. Captures the design conversation between the user and Junie verbatim so the implementation can resume in a later session without re-deriving any decision. No code lands in the session that produced this file.

    Companion files:

    • docs/dev/scratch/CHECKLIST-multiconfig-menu.md - the resumable step list that drives the implementation across sessions.
    • See "Mermaid chart" at the bottom of this file for the visual model of the new dispatch surface.

    1. One-paragraph summary¶

    The runtime book menu currently lets an admin browse and stage edits to the global config files (config.yml, safety.yml, etc.) via MenuAction.OpenConfigSelector and MenuAction.OpenConfigFile. This proposal extends that pattern to the per-entry config files held by MultiConfigParser<E> (today: regions/*.yml and worlds/*.yml; tomorrow: effects/*.yml and any further kinds), and adds the ability to create new entries (Add) and delete existing entries (Remove). Add/Remove are gated by a pluggable per-kind "in-use" guard so that the default region and any world currently loaded on the server cannot be removed via the book.

    2. Decisions captured from the user's review¶

    These are the answers the user gave during the proposal review on 2026-05-22. They are the contract this design is built against; do not silently change them in implementation.

    1. Region semantics. Local regions can be edited locally. Build on top of MultiConfigParser so the same menu pattern serves regions, worlds, effects, and any kind added later. Anything currently "in use" cannot be removed; the set of in-use predicates can grow arbitrarily as new kinds are added.
    2. World semantics. Worlds cannot be removed when the server reports the world by name (i.e. RTPServerAccessor.getRTPWorld(name) != null). Orphan world configs (server no longer reports the world) may be removed.
    3. API shape. Three new sealed MenuAction variants, all parameterized by a parserKind string that matches MultiConfigParser.name ("regions", "worlds", future "effects"). Not per-kind variants.
    4. Add UX. Add opens an anvil-text-input prompt (existing MenuAction.PromptAnvilInput + AnvilInputSession infrastructure from ADR-045). Prefill is default<N> where N increments until the candidate name is unique against the parser's existing entries. The user types over the prefill if they want a different name.
    5. Remove UX. Remove is a toggled mode on the selector page, not a per-row button. The viewer flips a toggle row at the top of the selector; while the toggle is ON, clicking any non-locked entry row dispatches a remove instead of an edit. The toggle is per-viewer, session-scoped, and resets on selector re-open.
    6. Locked row presentation. Locked entries (default region, live world) are shown as gray-disabled rows, not hidden. Hover text explains why they cannot be removed.
    7. Color scheme. Row labels are file names, not messages.yml strings, so they do not need per-locale color treatment. Hover text (and only hover text) is translated and lives in messages.yml.
    8. Seed for Add. Clone default. When the new entry's name (region kind) or world name (world kind) ends in _nether or _the_end, amend the cloned values the same way the existing SubConfigCmd region-update path does (LINEAR vert, direction=2, maxY=128, requireskylight=false for nether; requireskylight=false for the_end). The existing logic lives in SubConfigCmd.java lines 83 and 123; factor it into a reusable helper rather than duplicating it.
    9. Permission. Reuse rtp.config.edit for both Add and Remove. View gating uses the existing rtp.config.view. No new permission node.
    10. Out of scope. ADD does not create the server world (only the YAML config). No cross-server propagation. No new ADR for this slice (extends ADR-035 / config-view-as-book). A short subproject ADR is optional if implementation reveals an architectural decision worth capturing; default is no ADR.

    3. API surface¶

    3.1 New MenuAction sealed variants (in rtp-api)¶

    All three follow the defensive-copy / equals / hashCode / toString discipline of the existing OpenConfigSelector / OpenConfigFile / OpenConfigKey records, and are routed through the same MenuTokenRegistry mint path (one token per row, ADR-035 §3).

    /** List page for a MultiConfigParser kind (regions, worlds, effects, ...). */
record OpenMultiConfigSelector(String parserKind) implements MenuAction { ... }

/** Per-entry staging-cart page for one entry of a MultiConfigParser kind. */
record OpenMultiConfigEntry(String parserKind, String entryName) implements MenuAction { ... }

/** Server-resolved mutation against a MultiConfigParser kind. */
record MultiConfigMutate(String parserKind, String entryName, Op op) implements MenuAction {
    enum Op { ADD, REMOVE }
}

    parserKind is normalized to lowercase on construction. entryName is trimmed and validated against a conservative [A-Za-z0-9_.\-]+ regex (rejects YAML path traversal, slashes, whitespace, etc.); construction throws IllegalArgumentException on violation so a malformed token cannot ever reach the dispatcher.

    OpenMultiConfigSelector does not carry the remove-mode toggle state. The toggle is held by MenuRedeemSubcommand per-viewer (see §3.4); the selector builder reads the live toggle state when rendering and emits row actions accordingly. This keeps the action sealed-shape compact and avoids encoding ephemeral UI state into a token.

    3.2 In-use removal guard SPI (new, in rtp-core)¶

    package io.github.dailystruggle.rtp.common.commands.menu.multiconfig;

public interface MultiConfigRemovalGuard {
    /** Returns true when entryName must NOT be removed. */
    boolean isLocked(String entryName);

    /**
     * messages.yml key whose value is the hover-tooltip reason shown on the
     * locked, grayed-out row. Returning null means "no reason text".
     */
    @Nullable MessagesKeys reasonKey(String entryName);
}

    MultiConfigRemovalGuards (new) is a process-wide registry of Map<String /*parserKind*/, MultiConfigRemovalGuard>. The Bukkit-family wiring (RTPCmdBukkit) and the Fabric wiring register two default guards on plugin enable, before the first MenuRedeemSubcommand is constructed:

    • regions → locks entryName.equalsIgnoreCase("default"). Reason key: messages.multiconfig.lock.regionDefault (new).
    • worlds → locks RTP.serverAccessor.getRTPWorld(entryName) != null. Reason key: messages.multiconfig.lock.worldLoaded (new).
    • Unknown kind → falls back to a no-op guard that locks nothing. (Defense-in-depth: a kind that has no row in the admin panel will not have a selector page either, so this branch is reachable only if a forged token names an unregistered kind, which the dispatcher rejects upstream.)

    The dispatcher re-checks the guard server-side on every MultiConfigMutate(REMOVE, ...) dispatch. Row suppression in the builder is UX hygiene; the dispatch-side re-check is the actual invariant per the S-001 / D-005 pattern of "never trust the client".

    3.3 New builder: MultiConfigMenuBuilder (in rtp-core)¶

    Sibling to CommandTreeMenuBuilder (the existing OpenConfigSelector / OpenConfigFile builder), not folded into it. Three entry points:

    • buildSelector(UUID viewer, String parserKind, boolean removeMode) → the list page.
    • buildEntry(UUID viewer, String parserKind, String entryName, LinkedHashMap<String,String> cartSnap) → the per-entry staging-cart page. Cart snapshot keyed by (parserKind, entryName, fileName).
    • buildConfirmRemove(UUID viewer, String parserKind, String entryName) → tiny confirm page (single confirm button + cancel). Only used by Remove. Add does not need a confirm page because the anvil prompt itself is the confirmation step.

    Selector page layout (top to bottom, every row a single line so the book stays short):

    1. Back row → OpenConfigSelector (the main config-files page) so the user can navigate back up the admin tree.
    2. Header (non-clickable): the kind name, e.g. "Regions" or "Worlds".
    3. Toggle row: "[ ] Remove mode" or "[x] Remove mode" → re-opens the selector with removeMode flipped.
    4. Add row: "+ Add new..." → PromptAnvilInput prefilled with default<N>, whose confirm token redeems to MultiConfigMutate(parserKind, <typed>, ADD).
    5. One row per entry (alphabetically sorted; default first if present):
    6. Normal mode + non-locked → OpenMultiConfigEntry(parserKind, name).
    7. Normal mode + locked → same as above (locked entries are still viewable; lock applies only to remove).
    8. Remove mode + non-locked → red label, action = MultiConfigMutate(parserKind, name, REMOVE). Click goes through the confirm page.
    9. Remove mode + locked → gray label, no action (non-clickable display row), hover text from reasonKey.

    Entry page layout: mirrors the existing OpenConfigFile page (staging cart, Changeable list, Pending block, Apply, Discard). The only material difference: keys come from the per-entry ConfigParser<E> instead of a global parser. Apply still goes through the existing MenuRedeemSubcommand cart-apply machinery.

    All hover text on this surface is resolved through messages.yml keys; row labels are file names (no message key needed). The "header" row's label is a translated string (kind name); its message key is messages.multiconfig.header.<parserKind> with a generic fallback messages.multiconfig.header.default = "[parserKind]".

    3.4 Dispatch arms (in MenuRedeemSubcommand)¶

    Three new arms, each mirroring the existing dispatchOpenConfigSelector shape (gate → builder → render → S-004 reject on every failure path):

    • dispatchOpenMultiConfigSelector(senderId, OpenMultiConfigSelector open, messageMethod).
    • dispatchOpenMultiConfigEntry(senderId, OpenMultiConfigEntry open, messageMethod).
    • dispatchMultiConfigMutate(senderId, MultiConfigMutate open, messageMethod).

    Plus a new per-viewer state field Map<UUID, Set<String>> removeModeKinds holding the parserKinds for which the viewer currently has remove mode ON. The selector dispatch arm consults this map when building; the toggle row's action is a dedicated re-dispatch of OpenMultiConfigSelector after flipping the bit (no new sealed action variant for the toggle itself).

    Permission gating:

    • dispatchOpenMultiConfigSelector / dispatchOpenMultiConfigEntry: rtp.config.view.
    • dispatchMultiConfigMutate: rtp.config.view and rtp.config.edit. On REMOVE, additionally re-check the guard for the named entry; on a locked entry, reject with menuInvalid and log WARN (this is the S-004 path for "forged token attempted protected mutation").

    ADD path detail:

    1. The anvil-input prompt is opened by the row's PromptAnvilInput action (already platform-supported).
    2. The submit command in the anvil prompt is shaped to redeem a token that the renderer minted at selector-build time for MultiConfigMutate(parserKind, "", ADD). The dispatcher reads the typed text as the entry name (overriding the empty placeholder), validates it (regex, non-empty, not already present), then calls parser.addParser(name).
    3. After addParser returns, the dispatcher applies the nether/end amendment helper (extracted from SubConfigCmd lines 83/123 into a reusable NetherEndConfigAmender).
    4. The dispatcher re-renders the selector page so the new row is visible.

    REMOVE path detail:

    1. Click in remove-mode dispatches MultiConfigMutate(parserKind, name, REMOVE).
    2. Dispatcher gates on rtp.config.edit, re-checks the guard, then opens the confirm page (the confirm button mints a fresh MultiConfigMutate token; the cancel button mints OpenMultiConfigSelector(parserKind) with the toggle preserved).
    3. On confirm-click, dispatcher removes the parser from the configParserFactory map and schedules the YAML file for delete (mirroring SubConfigCmd lines 287-288: deleteOnExit()).
    4. Dispatcher re-renders the selector.

    3.5 Renderer (in rtp-paper-common BookMenuRenderer)¶

    Three new case arms in the action-to-token-mint switch, matching the existing config-subtree shape. No BookMenuRenderer logic changes beyond the three switch arms.

    3.6 Admin panel rows (in AdminPanelBuilder)¶

    Two new rows under the Configuration divider, both gated rtp.config.view:

    • "Regions" → OpenMultiConfigSelector("regions").
    • "Worlds" → OpenMultiConfigSelector("worlds").

    Effects and future kinds are not added in this slice. Doing so is a one-line addition once their MultiConfigParser is the canonical config surface and a removal guard has been registered for the kind.

    4. Locale strings (new messages.yml keys)¶

    Authored under the project's TSV pipeline (scripts/locale-files-to-csv.ps1 → reconcile-locale-csvs.ps1 → translate → locale-files-from-csv.ps1 → LocaleParityTest). All keys live under a new top-level multiconfig block; identity-mapped first-pass translations are acceptable for locales other than en and es per the project's translation guide.

    multiconfig:
  header:
    default: "[parserKind]"
    regions: "Regions"
    worlds: "Worlds"
  toggle:
    removeMode:
      off: "[ ] Remove mode"
      on:  "[x] Remove mode (click an entry to delete)"
  row:
    add: "+ Add new..."
    addHover: "Type a name in the anvil prompt. Prefilled: [name]"
    editHover: "Edit [name]"
    removeHover: "Delete [name]"
  confirm:
    title: "Delete [name]?"
    yes: "Confirm delete"
    no:  "Cancel"
  lock:
    regionDefault: "The default region cannot be removed."
    worldLoaded:   "World '[name]' is loaded on the server. Unload it before removing its config."
  result:
    added:   "Added '[name]'."
    removed: "Removed '[name]'."
    addFailed:    "Could not add '[name]': [reason]"
    removeFailed: "Could not remove '[name]': [reason]"
    nameInvalid:  "Name '[name]' is not allowed. Use letters, digits, '_', '-', '.'"
    nameTaken:    "An entry named '[name]' already exists."

    The [parserKind] and [name] placeholders follow the project's existing [token] placeholder convention and must be masked through the TSV translation step per the encoding/translation guide.

    7. Risks / open notes for the implementation session¶

    • Effects kind. EffectsGroupKeys is already a MultiConfigParser (see Configs.java line 280). Adding a third admin-panel row would require an in-use guard for effects (probably: "locked if any active player has the effect group attached"). Out of scope for this slice; flagged here so the next iteration can lift it in.
    • Confirm-page placement. The confirm page sits between the click and the actual mutation. If the user navigates away (back row or selector re-open) between click and confirm, the staged mutation is dropped silently (mirrors the existing staging-cart contract - see MenuRedeemSubcommand.clearCart).
    • Cart key collision. The existing staging cart is single-file scoped per viewer. For OpenMultiConfigEntry the scope becomes (parserKind, entryName, fileName). Keying must be updated everywhere the cart is read/written, but the cart's contract (one staged file per viewer) is preserved. This is the largest non-obvious risk in the implementation session; budget time accordingly.
    • Toggle persistence across navigation. Decision: the remove-mode toggle survives navigation to and from the entry page (so opening an entry to "double-check before removing" then going back leaves the mode ON). It resets when the viewer leaves the selector for a non-multiconfig page (back to OpenConfigSelector / admin panel / front page) or when the token TTL expires.
    • Folia / region thread. All file-system mutations (add/remove YAML files) must run on the async scheduler per S-005. Reuse RTP.scheduler.runTaskAsynchronously exactly as the existing SubConfigCmd.onCommand does.
